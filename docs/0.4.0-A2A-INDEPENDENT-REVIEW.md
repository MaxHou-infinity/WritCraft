## P1 finding（唯一阻断项）

**A2a 自己的 App 边界 E2E 门禁是不稳定的，并已真实红过一次。**

`tests/verify-v0-snapshot-create-list-electron.js` 在复审的**第一次**执行即失败：

```
AssertionError at tests/verify-v0-snapshot-create-list-electron.js:136
  actual   { error: true,  status: '本地快照私有目录无法安全使用。请确认项目仍可写后重试。' }
  expected { error: false, status: '本地快照已创建。' }
```

随后 7 次执行（3 次常规 + 3 次在 10 路 CPU 负载下 + 1 次插桩）**全部通过**。因此是
**间歇性红灯**，不是稳定红。

已定位机制：`renderer/project-home-view.js:440/456` 会触发**非 quiet** 的 `refresh()`；
一次非 quiet 的 `loadSnapshots`（`:156`）若在测试的 chmod 之后失败，会走到 `:172-173` 并把
状态文案覆盖掉（插桩运行观察到 create 窗口内确有并发的非 quiet
「正在读取已提交的本地快照…」）。即：**测试在断言 quiet-refresh 的状态保留语义时，没有等待
它自身的 view-change refresh 静默**，存在竞争窗口。

**为什么这构成 P1 而非 P2**：该测试是 A2a checkpoint 明确命名的 App 边界证据，且已注册进
0.4 清册（`stage A / lane snapshot-app / evidenceKind electron-e2e / requiresGui`）。
一个自己命名、被当作签收依据的门禁呈现非确定性，等于该 checkpoint 的证据不可靠——
这与"红灯藏在无人运行的脚本里"不同，它正是我们声称通过的那一项。
