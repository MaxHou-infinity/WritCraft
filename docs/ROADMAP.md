# 笔触 WritCraft 产品开发路线图 · RM-1.2

> 路线图版本：`RM-1.2`
> 生效日期：2026-08-01
> 当前公开产品版本：`writ-craft@0.1.1` Developer Preview
> 当前目标版本：`writ-craft@0.1.2`
> 当前目标：真实作者可用性闭环
> 状态：**当前开发顺序与版本边界的唯一权威**

本路线图把笔触从已经公开的 Developer Preview 推进到可持续使用、可以正式发布的个人写作产品。后续开发采用“目标模式”：任何时刻只有一个当前目标版本；新想法进入候选池，不得插入当前版本。

## 1. 权威边界

- **源码与可复现测试**回答“代码现在是什么”。
- `v0/DEVELOPMENT-STATUS.md` 回答“当前实际完成到哪里、有哪些红灯”。
- 对应 `docs/*-CONTRACT.md` 回答“当前功能如何验收”。
- `docs/WRITCRAFT-PRD-V3.md` 回答“产品必须做什么”。
- **本路线图**回答“下一版本做什么、按什么顺序、什么不能做”。
- `docs/PHASE-A-IMPLEMENTATION.md` 和后续技术规格回答“如何实现”。
- `deliverables/`、PDCA 和旧路线图只用于历史追溯，不得派发当前任务。

若文档冲突，先以源码和当前证据判定事实，再在同一工作批次修正文档；不得选择有利于继续开发的旧描述。

## 2. 两套版本号，禁止混用

### 2.1 路线图版本

- `RM-1.2`：以统一写作任务流替换真实作者否定的 Navigation → Research → Changes 默认多步旅程；不扩大 AI 写入权限或产品主线。
- `RM-2.0`：目标用户、商业模式或产品主线发生重大变化。

路线图版本不发布到 npm，也不创建同名产品 Tag。

### 2.2 产品版本

- Patch，例如 `0.1.2`：兼容性缺陷修复、稳定化和当前能力验收闭环。Developer Preview 中若真实验收证明已公开能力的产品假设失效，可在不扩大目标用户或写入权限的前提下，用最小替代交互修复；必须升级路线图版本并明确记录例外。
- Minor，例如 `0.2.0`：新增一组明确、可独立验收的用户能力。
- `1.0.0`：建立稳定兼容、正式用户支持与发布承诺。

产品版本只有完成本路线图规定的全部门禁并取得明确发布授权后，才能发布到 npm 或创建 GitHub Release。路线图规划版本不等于已经承诺发版。

## 4. 当前目标：`0.1.2` 真实作者可用性闭环

### 4.1 目标结果

证明 0.1.1 的核心能力能在真实长文中安全、可理解、可恢复地工作；对于真实验收已经推翻的公开 Plan 与 Navigation → Research → Changes 多步旅程，以不扩大写入权限的结构规划和统一写作任务流替代。该项属于 Developer Preview 的兼容性修复例外，不开放新的产品主线。

### 4.2 必须完成

1. 选择满足 `edit.md`、5 个以上 `chapters/` 章节、2000 个以上可见中文字符和至少 1 个 `references/` 文件的作者项目。
2. 只读预检原项目，在作者指定位置创建隔离副本，并证明原始快照未改变。
3. 按 `AUTHOR-ACCEPTANCE-V1-CONTRACT.md` 完成六段旅程：
   - 项目卡 → `edit.md` ChangeSet → 人工确认 → 磁盘落盘；
   - Inline 拒绝、接受、Safe Undo 与 Chapter；
   - 空项目“结构规划”比较、编辑和骨架创建；已有项目“写作导航”与统一任务流；
   - 从一张导航建议一次点击进入同界面正文 Diff；仅在来源确实不足时于同一任务内补充来源；
   - image-01 评分及插入/保留/废纸篓终态；
   - Graph 冲突、作者纠错、Issue→Changes 与重启恢复。
4. 诊断作者项目现场 `Graph INVALID_CACHE`，提供可理解的诊断、重建或恢复路径；不得靠删除作者数据或手工清缓存冒充修复。
5. 修复旅程中发现的 P0/P1 阻断项；P2 必须明确记录、分级并决定是否允许发版。
6. 记录内容无关的私有指标：Inline 接受率、导航建议帮助度/动作、Research 匹配判断、图片评分/采纳、耗时和稳定错误码。

### 4.3 明确不做

- 不新增项目驾驶舱或命令面板；结构规划/写作导航只替代当前失效 Plan，不扩成第二套 AI 系统。
- 不做云同步、多人协作、账户、收费或插件系统。
- 不做无关视觉重构。
- 不扩大模型供应商范围。
- 不因为验收不方便而降低真实项目、隐私或写入门禁。
- 不保留旧 Plan 为实验入口，不继续为其 Schema、字段长度或提示词打补丁。
- 不继续修补固定双动作、人工主张判断和 Research→Changes 公开多步旅程；旧服务只可作为内部能力或独立高级工具复用。

### 4.4 发版门禁

- 发现问题的预验收可以在开发中进行，但最终六段真实作者旅程必须绑定拟发布的 exact candidate commit；已有稿件旅程使用新的合格隔离副本并证明原始项目快照不变，空项目结构旅程使用新的独立空项目。
- 最终旅程后任何生产源码变化都会使受影响的人工证据失效：必须形成新 candidate，并在新的隔离副本重跑受影响旅程；只有不改变产品行为的文档收尾提交可以晚于候选。
- `Graph INVALID_CACHE` 有明确根因和产品终态。
- 当前源码完成定向测试、完整 `npm test`、`npm run verify`、强制真实 Electron 和必要的公网安装复验。
- 独立复审 P0/P1 为 0；保留所有红灯及解释。
- README、PRD、合同、状态账本、本路线图、Git 与 Nowledge Mem 同步。
- 取得所有者对 `writ-craft@0.1.2` 的单独发布授权。
- 只发布 npm `preview` 与 GitHub prerelease；不得移动 `latest`。

## 5. `0.2.0` 日常写作工作区

### 5.1 目标结果

作者每天打开项目后，可以立刻知道“项目进展如何、当前在哪里、接下来做什么”，不必在文件树、Graph、Sources、Changes 之间自行拼接状态。

### 5.2 计划范围

- **项目驾驶舱**：章节状态、字数、最近文件、待审 Changes、未解决问题和来源缺口。
- **章节大纲**：按 Markdown 标题生成当前文件结构并快速跳转。
- **快速打开**：统一查找文件、标题、实体和问题。
- **可恢复导航**：标签、当前文件、光标、选区和滚动位置保持现有权威语义。
- 所有驾驶舱卡片必须跳回文件、段落、证据或审阅对象，不能成为只读统计装饰。
- 本版本只聚合确定性本地状态并帮助定位，不调用 AI 生成“下一步建议”、不生成结构方案；AI 写作建议仍由 0.1.2 的“导航”入口负责。

### 5.3 明确不做

- 不修改 AI 生成协议。
- 不同时加入统一任务中心或多模型。
- 不做云端与多人协作。
- 不把 Graph 重做成独立知识库产品。

### 5.4 验收重点

- 外部文件变化后，大纲、字数和卡片状态准确更新。
- 键盘、窄窗口、长章节和 300 文件项目仍可用。
- 真实作者能从驾驶舱完成“定位任务 → 编辑 → 审阅 → 返回项目状态”的连续旅程。

## 6. `0.3.0` 透明 AI 协作

### 6.1 目标结果

作者始终知道 AI 正在做什么、实际读取什么、为什么被阻止，以及下一步可以采取什么动作。

### 6.2 计划范围

- **统一 AI 任务中心**：排队、预检、生成、校验、生成 Diff、等待审阅、完成/失败。
- 统一显示耗时、取消、可重试终态和后台完成状态；切换工作区不得丢失任务真相。
- **`@` 引用自动补全**：文件、文件夹、章节、实体、来源和图谱问题。
- 提交前展示 Context 清单、预算、截断和检索原因。
- Chat、导航、Chapter、Research、Graph handoff，以及所有生成后进入 Changes 的 AI 请求，统一采用分区化 `edit.md` 编译器；硬约束优先级和 revision/locator 语义一致。Changes 继续是审阅/应用边界，不新增独立模型请求。

### 6.3 明确不做

- 不让 AI 自动连续修改整个项目。
- 不同时接入大量模型供应商。
- 不加入跨项目记忆、付费套餐或团队能力。

### 6.4 验收重点

- 项目切换、revision 漂移、外部修改、取消、迟到结果和重复提交全部 fail-closed。
- 所有长任务都有真实阶段而非伪进度。
- 用户能从 Context 披露定位本次使用和未使用的项目规则。

## 7. `0.4.0` 证据与交付闭环

### 7.1 目标结果

笔触从“能协助写作”升级为“能把可信、可恢复的作品交付出去”。

### 7.2 计划范围

- 项目快照、比较与恢复。
- DOCX 或 PDF 中选择一种作为首个正式导出格式，不同时承诺两种。
- 导出前检查目录、脚注、图片、引用和缺失资源。
- Graph 共用同一证据模型提供关系图、时间线、实体表和论点—证据表。
- Research 引用健康度：缺来源、定位漂移、重复来源和单一证据提醒。

### 7.3 明确不做

- 不自动裁定观点真伪。
- 不在同一版本同时实现 DOCX 与 PDF。
- 不加入云备份、团队资产库或出版平台分发。

### 7.4 验收重点

- 快照和恢复不改变用户未选择的正文。
- 导出结果经过真实渲染检查，而非只验证文件存在。
- Graph/Research 的每项警告都能回到证据，且修复只生成可审查 Diff。

## 8. `1.0.0` 稳定个人写作产品

### 8.1 目标结果

成为方法论类长文作者可以持续使用、愿意推荐，并可承担正式项目的个人写作 IDE。

### 8.2 Go 门禁

- 至少 10 名真实作者完成内测；在看结果前冻结 Continue/Modify/Stop 指标。
- 安装、升级、迁移、恢复、备份、导出和问题报告形成完整用户闭环。
- 真实长项目的稳定性、可理解性和性能达到冻结门槛。
- P0/P1 为 0，生产依赖审计通过，发布迁移与回滚方案完成。
- `npm latest` 只能在正式 Go 决策和单独授权后移动。
- 独立签名 macOS App 是可选路线，不是 `1.0.0` 的自动门禁。

## 9. Pro 与 Team 候选池

### 9.1 Pro

只有 `1.0.0` 证明个人作者价值且取得真实付费意愿后才能立项：

- 更大上下文和用户显式授权的跨项目知识；
- 高级 Research、引用和一致性审计；
- 方法论手册、白皮书、行业报告等专业模板；
- 多模型选择、单次估算、项目预算和费用治理；
- 高级快照、恢复和优先支持。

### 9.2 Team

只有个人版与 Pro 稳定后才能立项：

- 作者、编辑、研究人员角色；
- 评论、建议、批准和版本流转；
- 团队术语、事实和来源资产；
- 权限、审计与私有部署。

移动端、实时多人协作、插件市场、语音/视频和“一键写完整本书”不在当前承诺中。

## 10. 目标模式执行协议

每个产品版本严格按以下顺序推进：

1. 冻结目标、范围、非目标和失败矩阵。
2. 更新或新增对应产品/技术合同。
3. 实现最小可运行纵切，不同时铺开多个跨层功能。
4. 运行定向测试并保留首个红灯。
5. 完成完整回归和真实 Electron 用户旅程。
6. 提交并推送拟发布的 exact candidate。
7. 在新的合格隔离副本上，使用该 exact candidate 完成真实作者或真实输出验收。
8. 独立复审；P0/P1 未清零不得签字。若修改生产源码，回到第 3 步，并使受影响的人工证据失效。
9. 同步 README、PRD、合同、状态账本和本路线图；文档-only 收尾可位于产品候选之后。
10. 更新并反查 Nowledge Mem。
11. 获得明确发布授权后才打产品版本标签、发布 npm 和创建 GitHub Release。
12. 发布后反查 registry、tag、公开安装和文档终态。

只有以下情况可以打断当前版本：

- P0/P1；
- 数据安全、正文丢失或越权风险；
- 当前版本验收所必需的缺口；
- 发布基础设施出现阻断。

其他新想法只记录到候选池，待当前版本签字后再决定是否进入下一次路线图修订。

## 11. 路线图变更规则

- 调整当前版本范围前，先记录为什么现有目标无法达成。
- 任何新增功能必须同时写明用户价值、非目标和验收标准。
- 不因单次测试绿灯提前移动版本状态。
- 不因额度不足把半成品写成“已完成”；应先更新状态账本和 Nowledge Mem。
- 已发布版本标签不可移动；补丁使用新产品版本。
- 本路线图的版本状态只有在 `v0/DEVELOPMENT-STATUS.md` 记录对应证据后才能从“计划”变成“已完成”。
