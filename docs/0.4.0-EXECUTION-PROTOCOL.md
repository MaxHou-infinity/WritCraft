# WritCraft 0.4.0 封版恢复执行协议

> 编号：`WRC-0.4.0-EXEC-R1`
> 生效日期：2026-08-11；治理修订：2026-08-13
> 状态：**当前派工控制文件；不改变 `WRC-0.4.0-R1` 的产品范围、失败矩阵、作者体验或发布边界**
> 当前锁定：**只推进 Stage A；Stage B 冻结等待真实 A→B 连续旅程；Stage C/D/E 不得开工**
> 旧版完整文本：[`archive/development/0.4.0-EXECUTION-PROTOCOL-R1-THROUGH-2026-08-13.md`](archive/development/0.4.0-EXECUTION-PROTOCOL-R1-THROUGH-2026-08-13.md)

本协议把 0.4.0 从多轮微签收恢复为受约束里程碑开发。它防止阶段跳跃、fake/component 绿灯冒充产品完成和全量回归浪费，但不把内部 schema、wire、locator 或 E/R/V/F slice 升级成新的 checkpoint。

## 1. 当前单一派工入口

Stage A 只按以下 checkpoint 顺序推进：

1. **A0 可执行门禁**：0.4 测试清册、静态 orphan check、current-component 顶级 gate。
2. **A1a finalize/ACK**：CREATE finalize/ACK cleanup。
3. **A1b mixed/rollback**：mixed EXISTING 与 `ROLLBACK_CREATE` 的同事务 authority。
4. **A1c Safe Undo**：permanent-journal Safe Undo 当前生产链。
5. **A2a create/list**：Main handler、IPC、preload、Renderer 创建/列出真实 committed snapshot。
6. **A2b compare**：snapshot compare、diff、stale/conflict 显示。
7. **A2c restore/undo**：选择性 restore、History reconcile、Safe Undo 用户链。
8. **A2d delete**：destructive confirmation、delete、committed reconciliation、刷新。
9. **A3 Stage A 签收**：helper package、完整门禁、真实 Electron、Computer Use、独立复审和 exact local checkpoint commit。
10. **A→B 重签**：只用 App 创建的真实 snapshot 重跑“创建→选择→预检”，不重写 Stage B 逻辑。

A1a–A2d 各自是一个独立 checkpoint，每项只在完整出口执行一次独立 review cycle。前一 checkpoint 未签收，不得并入下一项生产代码；以上十项未完成前不得实现 Stage C/D/E。

### 1.1 内部 slice 不是 checkpoint

E/R/V/F、schema、wire、locator、native bridge、CAS、pure helper 和 focused test 可以作为实现顺序与 component evidence，但：

- 不单独创建 final binding 或签收门禁；
- 不要求逐 slice 独立 reviewer、逐文件 hash 或 binary diff；
- 不因旧 review record 中的 `final binding pending` 阻断同一 checkpoint 内相邻实现；
- 不更新 roadmap、status、README 或 Nowledge 里程碑状态；
- 不能外推为 A1b、Stage A、App、candidate 或 release 完成。

现有 `0.4.0-A1B-E*-REVIEW.md` 只保留为 historical component evidence，不再拥有派工权。

## 2. Checkpoint 出口

### 2.1 A1 后端 checkpoint

A1a–A1c 出口要求：

1. 当前 authority/state/failure matrix 与已批准威胁模型一致；
2. 在声称的 production Main/native/filesystem 边界保留首个反例；
3. 最小生产路径可运行，不依赖 direct seed、no-op helper、fake receipt 或绕过 Main；
4. focused production integration、故障/漂移/response-loss 证据和测试注册通过；
5. 一个新的独立 reviewer 在实现稳定后完成一个完整 finding batch，修订后由同一 reviewer 定点确认 P0/P1 清零、P2 明确；
6. review 绑定一个 clean local checkpoint commit/tree。

A1 后端 checkpoint 不因未触及 GUI 而强制运行 Electron 或 Computer Use；这些证据在 A2/A3 的真实 App 边界补齐。

### 2.2 A2 App 与 A3 Stage

A2a–A2d 在上述基础上必须覆盖 production IPC/preload/Renderer 和受影响真实 Electron；涉及原生对话框、系统权限或视觉/OS 交互时再运行 Computer Use。A3 才运行完整 `npm test`、`npm run verify`、helper package、Stage A App/real-Electron/Computer Use 和 Stage exit review。

缺少对应层证据时，只能称为 component evidence 或 integration pending，不得称为 App、Stage、candidate 或 release 完成。

## 3. 安全边界与威胁分级

以下始终是 P0/P1 blocker：误写/误删、修改未选择文件、重放 mutation、跨项目污染、绕过 revision/owner、把 `UNKNOWN` 当成未提交清理、或丢弃已提交真相。

取消、冲突、项目切换和 proven pre-commit failure 必须零非预期公开写入。提交后响应丢失必须从持久真相返回 committed/committed-risk/locked truth，绝不重放；当自动收敛不可证明时，安全的 manual recovery 可以作为明确终态，不因可用性不完美自动升级为 P1。

阻断威胁模型覆盖真实本地事故：外部编辑器竞争、symlink/path escape、错误目标、crash/response loss、项目切换和并发 replacement。主动 same-UID 进程击穿 owner-only `0700/0600` 私有存储默认是 P2 hardening；只有所有者明确升级威胁模型后才可成为当前 checkpoint blocker。已冻结合同明确承诺的最大项数、字节预算和 fail-closed 上限仍是验收边界，不得降级；只有超出承诺上限的压力、不影响数据安全的 near-cap timing 和自动恢复可用性残余默认按 P2 评估。

同类 P1 连续两轮出现时，先判断其是否属于已批准阻断威胁模型。属于时暂停该 failure class、收齐完整状态矩阵后再修；超出时降级 P2/候选，不得借 review 自动扩大产品安全承诺。

## 4. WIP、测试与 review

- 同时只允许 **1 个主 checkpoint + 最多 1 个不修改同一 authority 的支持任务**；多个 agent 不得并行编辑同一状态机、schema 或事务链。
- 主 checkpoint 每个工作回合必须给出首红、最小实现、测试结果或明确 blocker；只有叙述、日志增长或更多 schema 不算进展。
- 先运行能跨越所声称边界的最小 focused gate；红灯先分类和定向复现，机械修改后不重复完整 suite。
- 新增或改名 `verify-v0-*.js` 必须在同一 change set 进入测试清册与当前顶级 gate；静态 orphan check 未绿时暂停实现。
- fixture seed、fake adapter、direct service、pure schema 和 component 数字不能签收跨层旅程；下游必须消费上游生产入口创建的真实产物。
- review 只在 checkpoint 实现稳定后开始。一个 review cycle 包含一次完整 finding batch 和修订后的定点确认；不为内部 slice 重复开启 final binding。

### 4.1 既有实现预检与分支生命周期

每个 checkpoint 开启后、首次修改生产代码前，先完成一次与当前 scope 成比例的既有实现预检：

1. 用 `git worktree list --porcelain` 与 `git branch -vv --all` 查明活动、失效和仅保留引用的 branch/worktree；
2. 对受影响文件和关键 authority/symbol 使用 `git log --all -- <files>` 与
   `git log --all -S'<symbol>' -- <files>`，不得只搜索当前分支；
3. 把命中的提交按当前 checkpoint 顺序标为：复用/移植、仅作对照、已被当前实现取代，或后续 checkpoint 候选；
4. 未完成上述分类前，不得在同一 authority 上重新实现；跨 checkpoint 分支不得整体合并，也不得用后续实现倒推前序 checkpoint 已签收；
5. branch/worktree 的 scope、当前 owner、退出条件和处置建议写入 checkpoint review material 或
   `docs/archive/engineering/` 的一次性对账记录，不用高频改写 status；删除 branch、prune worktree、改写历史或 push 仍需所有者明确授权。

预检只在 checkpoint 开启、发现新的并行实现或 scope/authority 变化时重做。不同独立根因的定向排障继续按首红推进；同一 failure class 连续出现时按 §3 的暂停规则处理，不以提交数量或调试轮数单独判定循环开发。

### 4.2 PDCA 纪律停止条件

以下条件是开工和继续工作的硬门禁，不是建议：

1. **Plan**：没有完成 §4.1 的分支/worktree/`git log --all` 对账，或没有把并行实现
   标记为复用、移植、对照、已取代或后续候选时，不得修改同一 authority，也不得向
   writer/agent 派工。发现未处置的并行分支时，先由 owner 决定合并、废弃或归档。
2. **Do**：同一功能必须在一次自洽 change set 中闭合源码、测试和必要控制文档；
   日常红绿结果追加到 archive，不用 status/docs 高频交替提交制造进度假象。
3. **Check**：每轮只报告首红、精确命令、实际结果和 evidence boundary。任何
   schema、focused、fake、seeded 或 direct-service green 都只能标记为 component
   evidence；若同一 failure class 第二次出现，必须暂停并重新检查 authority/state
   matrix，不能继续堆补丁。
4. **Act**：只有 checkpoint 开口、独立签收、Stage exit 或 scope/owner 决策才更新
   status、roadmap、contract、README 或 Nowledge。只有 clean exact tree + 独立 review
   才能形成 checkpoint commit；未闭合 WIP 不提交、不推送、不发布。
5. **记忆卫生**：Nowledge Mem 的新增或修订必须写明日期、scope、status、证据边界、
   supersedes 和 next decision。旧记忆保留为历史，但不得覆盖当前源码、status、
   contract 或 review；没有 clean checkpoint 与独立 review 的“implemented”只能作为
   historical/component-only，不能用于派工或解除冻结。

## 5. Clean checkpoint 与文档节奏

独立 review 只绑定一个 clean local commit/tree。reviewer 记录该 commit/tree 和必要测试结果即可；不再手工拼接 cumulative binary diff，不再以逐文件 hash manifest、chat-only signature 或不断变化的 status/INDEX 代替仓库 checkpoint。

若当前工作树无法形成 clean checkpoint，先暂停 review并建立 owner-approved isolation：整理 local commit、独立 worktree/branch，或其他能指向单一 tree 的边界。不得回退到全工作树 binary-diff fallback。任何 push、Tag、Release、publish 或 distribution 仍需所有者另行授权。

roadmap、status、受影响合同、README 和 Nowledge 只在以下 durable milestone 同步：checkpoint 开启、独立签收、Stage exit、范围/威胁模型决定。内部 component red/green、机械改动和 reviewer 定点复核不触发全套文档同步。

`v0/DEVELOPMENT-STATUS.md` 顶部只保留简短 current control block：checkpoint、目标、退出条件、最新 production red、开放 P0/P1/P2、focused command 和下一动作。详细轮次、旧测试总数和被取代的 checkpoint 进入 archive，不参与派工。

## 6. 暂停与当前冻结

只有以下情况需要暂停并向所有者升级：

- 需要改变 `WRC-0.4.0-R1` 产品范围、作者体验或已批准阻断威胁模型；
- 当前 checkpoint 需要第二套 Graph、索引、扫描器、History/recovery authority 或 Stage C/D/E 代码；
- 真实生产边界无法在当前或批准环境运行；
- 新测试无法注册，或无法形成 clean checkpoint tree；
- 已批准 blocker 的完整状态矩阵仍无法给出安全结果。

当前冻结不变：A0、A1a 已签收；只开放 A1b mixed EXISTING/`ROLLBACK_CREATE`。A1c、A2a–A2d、A3、A→B、Stage C/D/E 继续等待前序 checkpoint。单个 focused 绿灯不能删除整项冻结。
