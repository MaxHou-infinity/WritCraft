## 1. 产品定义

笔触 · WritCraft 是面向专业长文作者的 Cursor 式 AI 写作 IDE。它不把文章当成一个孤立输入框，而把一本书、一篇论文、一份报告或一个长篇故事视为包含规则、文件、段落、来源与关系的完整项目。

产品的核心承诺是：AI 能理解项目整体意图并协助跨文件工作，但所有正文和项目规则的修改都必须对用户可见、可审查、可接受、可拒绝、可撤销。

### 1.1 核心原则

1. **作者拥有最终控制权**：AI 只能提出建议或 Diff，不可静默修改正文、`edit.md` 或事实约束。
2. **上下文透明**：每次 AI 交互必须显示实际使用的项目规则、文件、选区、实体和来源。
3. **本地文件为真相来源**：正文以用户可直接读取、迁移和版本管理的 Markdown 文件保存。
4. **逐层协作**：同一套 AI 交互同时覆盖项目级、文件级和段落级，而不是把三者混成一个模糊的“全文”。
5. **图谱服务于诊断**：一致性星图必须能定位矛盾并回到证据，不能只做漂亮但不可操作的关系可视化。
6. **AI 不替用户做价值判断**：系统可以指出不一致、证据不足和偏离目标，但不能擅自决定观点优劣或改变作品立场。

## 2. 产品范围与对象模型

### 2.1 三级写作作用域

| 层级 | 对象 | 用户任务 | AI 默认上下文 | 典型操作 |
|---|---|---|---|---|
| 项目级 | 项目、`edit.md`、目录、全局图谱 | 定义主旨、目标、结构、规则；检查全局一致性 | `edit.md` + 用户显式引用 + 检索相关片段 | 项目问答、生成目录、跨文件修订、全局诊断 |
| 文件级 | 章节、场景、论证单元、素材文件 | 编写和修订一个完整内容单元 | `edit.md` + 当前文件 + 相关实体/文件 | 文件问答、章节总结、结构调整、全文 Diff |
| 段落级 | 当前选区、段落或句子 | 精确改写、扩写、缩写和校对 | `edit.md` 硬约束 + 当前选区 + 邻近段落 | `⌘K` Inline Diff、接受、拒绝、重载 |

作用域必须在 UI 中明确显示。用户未选择文字时，段落级命令不得假装拥有精确选区；跨文件操作不得在没有列出目标文件的情况下执行。

### 2.2 项目内容模型

```text
Project
├── ProjectPrompt (edit.md)
├── ContentFile[]
│   └── Block[]
│       └── TextRange / Citation[]
├── Source[]
├── Entity[]
├── Relation[]
├── TimelineEvent[]
├── ConsistencyIssue[]
└── ChangeSet[]
```

- **Project**：一个完整写作项目及其根目录。
- **ProjectPrompt**：根目录唯一的 `edit.md`，保存作者明确声明的意图和不变量。
- **ContentFile**：可编辑 Markdown 文件；文件夹只是组织结构，不是正文。
- **Block**：标题、段落、列表、引文等可稳定锚定的内容块。
- **TextRange**：块内的连续文本范围，是段落级修改的最小证据锚点。
- **Entity / Relation / TimelineEvent**：从正文和 `edit.md` 中抽取、经用户确认或编辑的语义对象。
- **ConsistencyIssue**：带证据和状态的不一致、遗漏、偏离或证据问题。
- **ChangeSet**：一次单文件或多文件 AI 建议的审查单元。

## 3. 项目生命周期

### 3.1 创建项目

首次创建项目时必须：

1. 让用户选择或创建本地项目文件夹。
2. 在根目录生成 `edit.md` 和 `.writcraft/project.json`。
3. 自动打开 `edit.md`，右侧 AI 进入“项目建立”对话。
4. AI 围绕主旨、目标读者、内容目标、范围、结构和约束逐项提问；用户可以跳过任何非必填项。
5. AI 对 `edit.md` 的填写建议必须通过 Diff 展示，用户接受后才落盘。
6. 用户确认项目框架后，可以由 AI 建议初始目录和文件；创建哪些文件仍需用户确认。
7. 项目建立模型只能返回严格结构化的 `summary`、`sections` 和 `fileSuggestions` 元数据，不得返回完整 `edit.md` 或建议文件正文；文件建议只包含安全的相对路径、标题和理由。
8. `edit.md` 必须由 Main 按 `writcraft.edit/v1` 确定性合并，保留既有 Front Matter、用户正文和自定义章节；Renderer 或模型不得成为最终文件内容的权威来源。
9. 建议文件默认是空白 Markdown 模板。用户在查看最终 `edit.md` Diff 和文件清单后必须进行第二次明确确认，未确认、拒绝或丢弃都不得写盘。
10. no-op 结果不得直接解锁写入；应用授权必须绑定当前项目、目标 revision、精确提案和一次性 capability，项目/revision 变化或提案被替换后立即失效。
11. 多文件创建必须 all-or-nothing：任何路径冲突、权限问题或写入失败都不得留下用户可见的部分创建结果，也不得要求用户逐个清理半成品。

### 3.2 打开项目

- 用户可以打开任意包含 Markdown 的文件夹。
- 若缺少 `edit.md`，应用提示“创建项目说明”，但允许只读浏览或继续写作，不强制阻塞。
- 若存在旧名 `editor.md` 且不存在 `edit.md`，应用提供一次性迁移预览；用户确认后改名，绝不静默覆盖。
- 恢复上次打开的文件、标签页、光标和面板状态；若磁盘文件已变化，应先提示冲突。

## 4. 根目录 `edit.md` 规范

### 4.1 定位与约束

`edit.md` 是项目级 Prompt，也是项目中最高优先级的用户意图来源。它必须位于项目根目录，文件名区分大小写时仍以全小写 `edit.md` 为规范名。

- 文件必须是标准 Markdown，脱离 WritCraft 仍可阅读和编辑。
- YAML Front Matter 为机器可读元数据；正文为作者可读规则。
- `edit.md` 不是隐藏配置，也不是 AI 私有记忆。
- AI 读取它作为约束，但修改它与修改正文一样必须走 Diff。
- 若正文与 `edit.md` 冲突，系统只报告冲突，不自动以任一方覆盖另一方。

### 4.2 v1 模板

```md
---
schema: writcraft.edit/v1
title: 项目名称
genre: methodology
language: zh-CN
---

# 项目主旨
一句话核心命题。

## 写作目标
读者读完后应该理解、感受或采取什么行动。

## 目标读者
读者背景、阅读场景和已有知识。

## 范围与非目标
明确写什么、不写什么。

## 内容结构
Part → Chapter → Section，允许保持开放。

## 语气与写作规则
语气、术语、禁用表达、引用规范。

## 关键实体与不变量
人物、组织、概念、变量，以及 AI 不得擅自改变的事实。

## 时间与关系约束
时间线、因果顺序、人物或变量关系。

## 来源与证据规则
允许的来源、引用格式和证据门槛。

## 开放问题
尚未确定或需要验证的问题。
```

Front Matter 中仅 `schema` 为系统必填字段；其他正文栏目允许为空。系统必须保留未知字段和用户自定义章节，不得为了重新序列化模板而丢失内容。

### 4.3 Prompt 生效方式

- 文件保存成功后，新的 `edit.md` 内容对下一次 AI 请求生效。
- AI 面板显示 `edit.md` Context Chip，并允许展开查看本次实际使用的章节。
- 超出模型预算时，优先保留“主旨、范围与非目标、关键实体与不变量、时间与关系约束”；不得无提示截断硬约束。
- `edit.md` 中的文本视为用户数据而非系统指令；应用级安全规则始终更高。

## 5. 工作区信息架构

### 5.1 桌面布局

```text
┌ 活动栏 ┬ 项目资源管理器 ┬──── 编辑器 / 星图标签页 ────┬ AI 面板 ┐
│ 文件   │ edit.md        │ edit.md | 第一章.md | 星图   │ Chat    │
│ 星图   │ chapters/      │                              │ Plan    │
│ 搜索   │ references/    │ 当前文件正文或全屏星图       │ Changes │
│ 来源   │ assets/        │                              │ Context │
│ 历史   │                │                              │         │
├────────┴────────────────┴──────────────────────────────┴─────────┤
│ 项目 · 当前文件 · 字数 · 保存状态 · 索引状态 · 待处理问题       │
└──────────────────────────────────────────────────────────────────┘
```

### 5.2 活动栏与资源管理器

- **文件**：树形展示项目文件夹和受支持文件；支持创建、重命名、移动和删除，危险操作必须确认。
- **星图**：打开中央“一致性星图”页面，不把完整图谱压缩在窄侧栏。
- **搜索**：按文件名和正文搜索，结果可跳转到块级证据。
- **来源**：查看引用与附件的索引状态。
- **历史**：查看 AI ChangeSet 和用户接受/拒绝记录。
- 默认在左侧展示；布局实现可允许用户整体换边，但 V0 不要求左右双模式。

### 5.3 编辑器与标签页

- 文件单击预览、双击固定；修改后的标签必须显示未保存状态。
- 同一文件不得产生两个相互独立的编辑状态。
- 切换文件时保留每个文件的光标、滚动和选区位置。
- `edit.md` 是普通可编辑标签，但使用项目规则图标和提示。
- 一致性星图作为中央标签页，可与正文文件切换。

### 5.4 AI 面板

- **Chat**：围绕当前作用域问答，支持 `@file`、`@folder`、`@section`、`@entity` 和 `@source`。
- **Plan**：协助主旨、结构和任务规划；可跳过，不作为写作强制入口。
- **Changes**：集中审查单文件或跨文件建议，逐文件查看 Diff、接受或拒绝。
- **Context**：展示本次请求的上下文清单、估算规模、截断或检索原因。

## 6. AI 上下文契约

### 6.1 优先级

每次请求按以下顺序组装；序号越小优先级越高：

1. 应用安全、隐私和不可越权规则。
2. 用户本次明确指令与目标作用域。
3. `edit.md` 中的项目硬约束。
4. 当前选区、段落及其邻近上下文。
5. 当前文件的相关结构与内容。
6. 用户显式引用的文件、章节、来源和实体。
7. 一致性星图中与任务相关、带证据的实体与关系。
8. 从其他项目文件中检索出的相关片段。
9. 最近对话摘要。

低优先级内容不得覆盖高优先级约束。若上下文存在冲突，模型应指出冲突并请求用户在 Changes 中决策，不得自行调和成一个新事实。

### 6.2 Context Chips

每次 AI 回复必须能够追溯到一组 Context Chips。至少包括：

- 作用域（项目 / 文件 / 选区）；
- `edit.md`；
- 当前及显式引用文件；
- 被检索片段的文件与标题；
- 使用的实体、关系和来源；
- 被省略或截断的上下文提示。

点击 Chip 应打开来源或解释为何被选中。模型不得声称“已阅读全项目”，除非系统实际索引并发送了完整项目内容。

### 6.3 跨文件修改

跨文件请求先生成计划，列出目标文件和修改理由，再生成 ChangeSet。ChangeSet 必须满足：

- 每个文件独立 Diff；
- 支持逐文件、逐块接受或拒绝；
- 接受前检查目标文件自建议生成后是否改变；
- 部分接受后保留其余建议状态；
- 所有接受操作进入撤销和审计历史；
- 不允许用“一键接受”绕过未展示的修改。

## 7. 一致性星图

### 7.1 产品目标

一致性星图是项目语义与冲突诊断页面。它需要回答三个问题：

1. 这个项目有哪些关键主体、概念、变量、事件和证据？
2. 它们在不同文件中如何关联和演化？
3. 哪些地方出现矛盾、遗漏、漂移、缺证或偏离项目主旨？

默认显示“当前文件相关子图”；用户主动切换后才显示全项目图，以避免大项目产生不可读的节点云。

### 7.2 统一图谱数据模型

#### 节点 Node

```json
{
  "id": "entity_person_001",
  "type": "person",
  "label": "林舟",
  "aliases": ["小林"],
  "summary": "故事主角",
  "attributes": { "age": 32 },
  "confidence": 0.96,
  "status": "confirmed",
  "evidenceIds": ["ev_001"],
  "updatedAt": "2026-07-15T00:00:00.000Z"
}
```

节点类型枚举：`person`、`organization`、`place`、`event`、`time`、`concept`、`principle`、`claim`、`variable`、`case`、`datum`、`source`、`foreshadow`、`open_question`。允许未来加类型，但读取未知类型时必须降级为通用节点而不是丢弃。

#### 关系 Edge

```json
{
  "id": "edge_001",
  "type": "contradicts",
  "from": "claim_001",
  "to": "claim_002",
  "directed": true,
  "label": "统计口径不同",
  "confidence": 0.88,
  "status": "proposed",
  "evidenceIds": ["ev_010", "ev_011"]
}
```

关系类型枚举：`supports`、`contradicts`、`causes`、`influences`、`depends_on`、`before`、`after`、`example_of`、`cites`、`explains`、`foreshadows`、`resolves`、`belongs_to`、`participates_in`、`mentions`。

#### 证据 Evidence

```json
{
  "id": "ev_001",
  "filePath": "chapters/01-introduction.md",
  "blockId": "blk_83c1",
  "start": 12,
  "end": 18,
  "quote": "林舟三十二岁",
  "contentHash": "sha256:...",
  "capturedAt": "2026-07-15T00:00:00.000Z"
}
```

证据必须使用项目相对路径，并同时保存块标识、范围、短引文和内容哈希。文件修改后先用块标识与哈希重定位；无法可靠重定位时标记 `stale`，不得跳到猜测位置。

#### 一致性问题 Issue

```json
{
  "id": "issue_001",
  "type": "attribute_conflict",
  "severity": "warning",
  "title": "人物年龄前后不一致",
  "description": "第一章为 32 岁，第三章为 35 岁，时间线仅过去一年。",
  "nodeIds": ["entity_person_001"],
  "edgeIds": [],
  "evidenceIds": ["ev_001", "ev_021"],
  "status": "open",
  "resolution": null
}
```

Issue 类型首批支持：

- `attribute_conflict`：人物、组织、概念属性前后不一致；
- `timeline_conflict`：时间倒置、不可能间隔或循环依赖；
- `variable_drift`：变量定义、单位、统计口径漂移；
- `claim_conflict`：原则或论点互相冲突；
- `evidence_gap`：论点缺少来源，或案例不能支持结论；
- `unresolved_foreshadow`：伏笔未回收；
- `orphan_entity`：关键实体被引入后长期遗漏；
- `prompt_drift`：章节逐渐偏离 `edit.md` 主旨、范围或结构。

严重度为 `info`、`warning`、`error`；状态为 `open`、`acknowledged`、`resolved`、`dismissed`。用户的忽略和解决决定必须持久化，重新索引不得无故复活相同问题。

### 7.3 星图交互

- 节点大小表示关联度，不得暗示内容价值高低；颜色只表示类型或问题状态。
- 支持搜索、类型筛选、文件范围、时间范围和“仅看问题”。
- 点击节点展示属性、关系和证据；点击证据打开对应文件并滚动到段落。
- 点击问题展示冲突双方；“建议修复”只创建 Diff，不直接修改原文。
- 用户可以合并别名、确认或否定抽取结果、编辑属性；确认结果作为后续抽取约束。
- 图谱数据属于派生数据，删除或重建图谱不得修改正文。

## 8. 用户控制、隐私与故障安全

### 8.1 写入控制

- AI 只读操作无需确认；创建、重命名、移动、删除文件或修改内容必须显示将发生的动作。
- 单文件段落修改使用 Inline Diff；多文件修改使用 Changes 面板。
- `edit.md` 的变更不得批量静默接受。
- 删除文件进入应用内可恢复区或使用系统废纸篓，不做不可恢复删除。

### 8.2 数据与网络

- 默认将项目正文、索引、图谱和历史保存在项目本地。
- 发往模型的每次上下文必须能在 Context 面板中解释；不发送未纳入请求的整个项目。
- API Key 不写入项目目录、正文、日志或 ChangeSet。
- 正式 API 配置必须存入稳定的应用级 userData；升级或开发 profile 迁移不得覆盖更新配置，也不得让 E2E 读取或改写真实用户 Key。设置面板打开时不自动联网，连接检测必须由保存动作或用户显式触发。
- 日志默认不记录正文全文；诊断导出前必须让用户预览和脱敏。
- 诊断预览必须显示将要写出的完整字节，并明确排除正文、来源文字、Prompt、模型回答、Key、项目/文件名和路径；Renderer 只能返回短期 token，输出路径与不可覆盖写入由 Main 和原生保存窗口掌握。
- Renderer 是离线文档表面：CSP 禁止连接，Electron session 继续拦截 HTTP(S) 与 WS(S)，并默认拒绝浏览器和设备权限；Renderer 不持有 Key 或网络原语。
- 作者证据指标保持项目私有和内容无关：只允许 workflow、结果、耗时、字符计数与时间，不记录正文、Prompt、答案、模型原文、错误消息、Key 或路径；旧指标文件必须兼容，小样本不得包装成结论。
- 图片评审证据与通用指标分离：通用指标记录生成耗时/安全结果；图片评审只记录 operation、1–5 分、插入/保留/废纸篓、可选人工核对费用和时间。生成不得改正文，删除必须移动 Main 绑定的精确资产到项目私有可恢复废纸篓。
- Main 的 V0 远端 allowlist 仅为文本 `api.minimaxi.com/anthropic/v1/{models,messages}` 与图片 `api.minimax.io/v1/image_generation`，不得接受 Renderer 提交 URL、主机、Key 或输出路径。
- 网络请求必须有请求/响应字节上限、贯穿响应体读取的 deadline、项目 owner abort、禁止重定向和写操作自动重试；远端 body、Prompt、正文、Key 与未知异常不得进入日志或用户错误。
- 所有 AI 请求必须绑定可信 sender、origin project instance 和 mutation generation；项目切换、正文/结构提交或外部权威文件变化后必须中止在途请求并拒绝发布陈旧结果。

### 8.3 保存与冲突

- UI 必须区分“编辑中”“正在保存”“已保存”“保存失败”“磁盘冲突”。
- 保存失败时不得清除内存中的未保存内容。
- 外部程序修改当前文件时，系统不得直接覆盖；应提供比较、保留本地或重新载入。
- 应用崩溃后应恢复未落盘草稿，并明确标记其来源。

## 9. 非目标（V0）

- 多人实时协作、移动端、语音、TTS 和视频生成。
- 一键生成整本书或让 AI 自主连续改写整个项目。
- 模仿在世或已故作家的专属文风。
- 让图谱成为独立知识库产品；V0 只服务当前写作项目。
- 自动替用户裁定观点真伪；系统只报告证据和冲突。

## 10. 产品验收

### 10.1 Phase A：项目工作区地基

1. 可创建或打开本地项目，首次创建会生成规范 `edit.md`。
2. 左侧文件树展示项目结构，用户可在至少两个 Markdown 文件之间切换编辑。
3. 保存后重新启动应用，文件内容、标签和基本工作区状态可恢复。
4. 文件写入采用安全保存；非法路径和越出项目根目录的请求被拒绝。
5. `edit.md` 保存后被下一次 AI 请求引用，Context 中可见。
6. 旧单文档草稿不会被静默丢弃，迁移过程可预览和取消。

### 10.2 Phase B：跨文件 AI

1. Chat 能明确区分项目、文件和选区作用域。
2. `@file` / `@section` 引用可跳转并出现在 Context Chips 中。
3. AI 对两个以上文件的修改以 ChangeSet 展示，逐文件接受和拒绝均正确。
4. 修改目标在建议后发生变化时，接受操作被阻止并要求重新生成或人工合并。
5. 所有已接受 AI 修改可撤销，并能在历史中追溯。

### 10.3 Phase C：一致性星图

本节的动态旅程、零写入边界、可访问性、最小窗口和大型图谱性能门禁由 `docs/GRAPH-ACCEPTANCE-V1-CONTRACT.md` 细化。产品契约于 2026-07-22 签字，2026-07-23 性能批源码完整 test/verify 与强制 Electron 连续两轮 26/26 通过，可见帧性能复审 P0/P1/P2=0。后续 Graph 韧性批又关闭完整语义权威、不可变快照、异步所有权与 Unicode quote 边界；当前最终源码完整 test/verify 通过、总链强制 Electron **31/31**，既有独立复审 P0/P1/P2=0。不得用 Node/源码字符串绿灯替代真实 Electron 验收。

1. 能从至少三个项目文件增量生成统一节点、关系、证据和问题。
2. 默认显示当前文件子图，可切换全项目并按类型、文件和问题筛选。
3. 至少准确演示人物/变量属性冲突、时间冲突、证据缺口和主旨偏离四类问题。
4. 属性冲突、时间冲突和主旨偏离必须至少有两个可点击证据；证据缺口必须至少有一个可点击的“待补来源”主张证据，并明确显示缺失标记，不得伪造第二条来源。文件变化导致锚点失效时显示 `stale`，不错误跳转。
5. 用户确认、忽略或解决问题后，状态在重启和重新索引后保留。
6. “建议修复”只产生可审查 Diff，图谱本身不会修改正文。

### 10.4 完整 V0 体验

以一个包含 `edit.md`、不少于五个章节文件和来源材料的真实项目完成：项目定义 → 文件写作 → 段落 Diff → 跨文件修改 → 一致性检查 → 重启恢复。验收必须包含真实 Electron 行为测试；仅检查 DOM 元素或源码字符串不能证明完成。完整 V0 还需关闭真实 GUI 项目卡落盘、完整 `sk-api-` 图片、真实作者长文与价值指标、干净打包、签名/公证/Gatekeeper 门禁；精确顺序与命令以 `v0/DEVELOPMENT-STATUS.md` 为准。
