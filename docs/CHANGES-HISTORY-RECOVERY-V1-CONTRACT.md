# Changes / History Recovery v1 Contract

> Status: **ordinary Changes contract implemented and signed on 2026-07-26 (P0=0/P1=0/P2=0); 0.4.0 Snapshot extension under Stage A independent review**
> Scope: ordinary Changes apply, reject-only review audit, History undo, Snapshot selective Markdown restore/Safe Undo recovery authority, process/Renderer response loss, and post-commit bookkeeping failure. Research and Inline retain their signed higher-level protocols but must obey the same project mutation guard.

## 1. Product truth

A failed IPC response is not proof that manuscript files were unchanged. Before the first manuscript or History write, Main must persist one project-scoped transaction marker at:

`/.writcraft/recovery/changes-history-transaction.json`

The marker is recovery intent, not manuscript truth. It binds a high-entropy operation ID, project ID, operation kind (`apply`, `review`, `undo`, `snapshot_restore`, or reserved `snapshot_restore_undo`), pending capability where applicable, exact affected paths, operation-before/after authority, the validated base/prepared History authority, and timestamps. It never stores API keys, prompts, model responses, absolute paths, or renderer DOM.

Old signed v1 inline markers remain read-compatible and remain the only production write route for ordinary apply/review/undo while their exact marker is at most 96 MiB. An ordinary transaction that would exceed that cap fails closed before marker or manuscript write; it must not silently enter the artifact route.

Snapshot recovery requires a small control record: each file carries only relative path, before/after existence and revision, plus nullable `createdIdentityDigest`; History carries existence plus digest; `artifact` carries exact schema, opaque basename derived from the operation ID, byte length, SHA-256, and base/prepared History digests. Every newly persisted History v4 application-file record additionally has exact `ancestorIdentityDigest`: ordinary Changes records use literal null, while Snapshot-restore records require the non-null sealed parent-selection ancestor digest for that same path/revision. Read compatibility for a pre-extension ordinary `changes/v4` record that lacks this field is narrow: Main first validates its complete old exact file shape and old integrity, then normalizes it in memory and on the next save to literal null. A mixed-shape record or any Snapshot-restore record without the sealed non-null ancestor digest fails closed; Main never inserts an inferred path identity. Snapshot template preparation, receipt materialization, undo preparation, delta reconstruction, restart and minified/raw History validation preserve the bound digest byte-for-byte, so an `entryId` alone can reproduce the complete Safe Undo parent authority without scanning a path or inventing an ancestor. Exact file bytes, one serialized base History, and a reconstructible prepared-History delta live in one separately fsynced, hash-bound binary artifact in the same private `0700` recovery directory. The delta names retained base entry IDs and stores only new/replaced entry metadata; its file-state data references the artifact's single raw-byte copy. The artifact uses the fixed `WRCCHRA2` length-prefixed format and is inspected incrementally; Main must never synchronously read or `JSON.parse` a 512 MiB marker.

The production artifact route is gated on an injected native exact-lifecycle adapter with distinct rollback and cleanup operations. The production adapter is `writcraft.changes-history-artifact-lifecycle/v1`; `forProject(rootPath)` creates a private scoped adapter, after which cleanup operations accept only a bounded artifact basename, held fd, expected identity, byte length, and SHA-256—not an absolute path or artifact bytes. The signed helper inherits a Main-owned read-only filesystem-root fd, receives the canonical absolute root only in its startup bind record, walks every component with no-follow `openat`, descriptor-opens the fixed owner-safe `.writcraft/recovery` directory, and rewalks the complete root/private chain at authority boundaries. Before any control access it independently requires fd 4 to be `O_RDONLY`, a regular file owned by the effective/expected uid, exact `0600`, and `nlink=1`; a writable fd, unsafe mode, unexpected owner, or multiply-linked source fails before control or artifact mutation. Once exact unlink may have committed, Main uses record reconciliation instead of weakening that fd precondition; reconciliation durably creates the exact reconstructed receipt when proof is exact and both source/quarantine names are absent. The adapter implements no-clobber `renameatx_np` quarantine, reopens and compares the exact inode identity and digest, unlinks only the quarantined identity, fsyncs the directory, and reconciles committed/unknown outcomes. Node path-based `lstat → unlink` is forbidden. Until that adapter exists and is wired, Snapshot recovery fails before artifact, marker, History, or Markdown writes with `ARTIFACT_CLEANUP_UNAVAILABLE`. Focused tests may inject an explicitly test-only fake adapter; that is mechanical evidence, not production closure.

Snapshot limits are 300 Markdown files, 64 MiB for snapshot-after bytes, 128 MiB for current-before plus snapshot-after bytes, 192 MiB for serialized base History, 32 MiB for the reconstructible prepared delta, 96 MiB for old inline-marker read compatibility, and 384 MiB for the binary artifact hard cap. The new control fixture must remain below 2 MiB at the 300-file maximum. An exact byte accountant covers magic, counts, every length prefix/path/state/identity, base History, prepared delta, and payload bytes; small real artifacts must equal the accountant, while the frozen 128 MiB raw + 192 MiB base + 32 MiB delta combination must remain below the artifact cap. Neither raw bytes nor a second complete History may be duplicated to make the accountant pass.

One project may have at most one unresolved Changes/History transaction. Marker path, schema, byte limits, symlink/hard-link behavior, exact keys, NFC paths, revision hashes, History integrity, and atomic/fsync persistence fail closed.

### 1.1 Public-Markdown phase extension (Stage A freeze)

Missing-leaf restore cannot know `createdIdentityDigest` until native code has successfully performed `O_EXCL`, written the exact Snapshot bytes through the returned fd, and fsynced that fd and its parent. Therefore Snapshot recovery extends the **same** Changes/History marker with one optional `publicMarkdownPhase` subrecord; it does not create another History file, recovery marker, scanner, capability store, or generic recovery writer. Its schema is `writcraft.changes-history-public-markdown-phase/v1`, validated by `snapshot-public-markdown-phase-schema.js`.

The parent marker/artifact first freezes one exact selection authority with schema `writcraft.changes-history-public-markdown-selection/v1`. Its exact fields are `schema`, operation `kind`, and ordered dense `selected`. Every selected item exact fields are `selectedId`, `action`, relative Markdown `path`, snapshot-after `revision`, and `ancestorIdentityDigest`. Restore permits only actions `EXISTING|MISSING`; Safe Undo permits only `EXISTING|CREATED`. Selected IDs and paths are unique and the full array is bounded to 300. Its digest is the repository-wide 3.1.4 authority from `evidence-delivery-schema`: `UTF8("writcraft-digest/v1") || 0x00 || UTF8("writcraft.changes-history-public-markdown-selection/v1") || 0x00 || canonicalJson(full exact parent binding)`, followed by complete SHA-256. Canonical object keys use Unicode code-point order; insertion-order `JSON.stringify`, concatenated fields, ID-only digests, and a second local canonical algorithm are forbidden. This parent authority is derived from the sealed comparison/current-state/History inputs; a phase caller cannot supply an unverified classification.

The phase subrecord exact fields are `schema`, `operationId`, `kind`, `phase`, `artifactDigest`, `selectionDigest`, `items`, `preparedHistoryDigest`, `finalReceiptDigest`, `existingReceiptSetDigest`, `rollbackReceiptDigest`, and `updatedAt`. `selectionDigest` must equal the digest of the descriptor-validated parent mapping passed separately to the validator. `items` must equal, entry for entry and in parent order, the **complete** `MISSING` subset for restore or the complete `CREATED` subset for Safe Undo. It cannot omit a second missing/created leaf, insert an `EXISTING` leaf, reorder a leaf, or change its selected ID, path, revision, or ancestor digest. Existing selected files remain represented by the parent marker/artifact and never receive a fabricated created identity. Each phase item exact fields are `selectedId`, relative Markdown `path`, snapshot `afterRevision`, `ancestorIdentityDigest`, nullable `createdIdentityDigest`, nullable `creationReceiptDigest`, and nullable `quarantineReceiptDigest`. All transitions retain operation ID, kind, artifact digest, parent selection digest, derived subset authority, and every already-populated receipt/identity/receipt-set digest. A project switch, parent reorder/drift, ancestor/content drift, changed receipt, skipped phase, duplicated path/ID, cross-branch transition, terminal replay, or phase rollback fails closed.

Every parent/phase record and nested item is a descriptor-validated plain exact data record. Parent `selected` and phase `items` are descriptor-validated dense plain arrays. Symbols, non-enumerable properties, accessors, sparse indices, named array properties, prototype variation, and unknown keys are rejected without invoking a getter. Both full selection and derived subset are bounded to 300.

Allowed direct transitions are conditional on the complete parent selection:

- all-missing restore (no `EXISTING` parent item): `PRECREATE → CREATED_RECEIPT → HISTORY_COMMITTED → FINALIZED`;
- mixed restore mainline: `PRECREATE → CREATED_RECEIPT → EXISTING_COMMITTED → HISTORY_COMMITTED → FINALIZED`;
- mixed restore zero-write branch, legal only after the existing-file executor has formally proved `UNCOMMITTED` with every existing leaf durably restored to its sealed before state and History still at its exact raw base: `CREATED_RECEIPT → CREATE_ROLLBACK_QUARANTINED → ROLLED_BACK`;
- created-leaf Safe Undo mainline: `PRECREATE → QUARANTINED → HISTORY_COMMITTED → FINALIZED`;
- created-leaf Safe Undo zero-write branch after a pre-History abort: `QUARANTINED → RESTORED`.

`ROLLED_BACK` is terminal and means the complete mixed selection and exact raw History equal operation-before. Safe Undo `RESTORED` is terminal and means `RESTORE_QUARANTINE` durably restored every receipt-owned CREATED leaf while History still equals the exact raw base. `FINALIZED`, `RESTORED`, and `ROLLED_BACK` have no outgoing transition. `UNKNOWN` is not a phase and cannot be CAS-persisted as progress: an unknown CREATE, existing-file execution, rollback-create quarantine/finalize, Safe Undo quarantine/restore/finalize, root/ancestor check, History state, receipt, or response leaves the prior exact phase locked for fresh reconciliation. Full-missing restore cannot enter either existing/rollback phase; mixed restore cannot jump directly from `CREATED_RECEIPT` to `HISTORY_COMMITTED`; mainline and rollback branches cannot cross; Safe Undo cannot move backward from `QUARANTINED` to `PRECREATE` or cross from `RESTORED` into the undone-History mainline.

Nullability is authority, not convenience:

- restore `PRECREATE`: every item in the missing-leaf subset has null `createdIdentityDigest` and `creationReceiptDigest`; `preparedHistoryDigest` and `finalReceiptDigest` are null, and quarantine receipt is always null. Existing selected leaves do not appear in this subset;
- restore `CREATED_RECEIPT`: every item in the same missing-leaf subset has its native-created identity and durable creation-receipt digest, and the exact prepared-History digest for the complete mixed existing+missing selection is now derivable and non-null;
- mixed restore `PRECREATE|CREATED_RECEIPT`: `existingReceiptSetDigest` is null. `EXISTING_COMMITTED`, both rollback phases, `HISTORY_COMMITTED`, and `FINALIZED` require the same non-null digest. On the mainline it binds the complete ordered parent-derived `EXISTING` receipt set proven committed; on the rollback branch it binds the complete formal `UNCOMMITTED` result proving every existing leaf is durably at before. Full-missing restore and every Safe Undo phase require this field to remain null;
- restore `CREATE_ROLLBACK_QUARANTINED`: every missing-subset item additionally carries its durable rollback-create quarantine receipt, while top-level `rollbackReceiptDigest` remains null. `ROLLED_BACK` retains the same item receipts and is the only phase with a non-null aggregate `rollbackReceiptDigest`. Every non-rollback phase and every Safe Undo phase requires that top-level field to remain null;
- undo `PRECREATE`: every target already carries the `createdIdentityDigest` sealed in the applied Snapshot History entry and its prepared undone-History digest is non-null; creation receipt is null;
- undo `QUARANTINED`: every target additionally carries the durable native quarantine-receipt digest;
- undo `HISTORY_COMMITTED` retains those receipts and the exact prepared-History digest after the undone History is durable;
- undo `FINALIZED` carries the non-null `FINALIZE_UNDO` final-record digest, while terminal `RESTORED` retains the same quarantine receipts/prepared-History digest and carries the non-null `RESTORE_QUARANTINE` final-record digest; neither terminal has an outgoing phase.

The binary artifact remains the single immutable byte authority for operation-before/after Markdown, exact raw base History, and a prepared-History **template**. In restore `PRECREATE`, the template deliberately contains a typed created-identity placeholder rather than an invented digest, so the marker's `preparedHistoryState` is nullable only in that phase. Native creation returns the exact identity/receipt; Main validates it against the immutable artifact path, after revision, bytes, ancestor digest, operation ID, and project instance, deterministically materializes the final History entry, and CAS-persists `CREATED_RECEIPT` in the existing marker. The artifact payload is not rewritten in place and no impossible syscall-level multi-file atomicity is claimed. For mixed restore, the existing-file executor must then reach a formal three-state result on the complete parent-derived `EXISTING` subset. `COMMITTED` alone advances to `EXISTING_COMMITTED`; `UNCOMMITTED` alone may enter rollback-create; `UNKNOWN` advances nowhere. History is CAS-written only from all-missing `CREATED_RECEIPT` or mixed `EXISTING_COMMITTED`, from the sealed raw base to the derived prepared digest, after which the marker advances to `HISTORY_COMMITTED`. Restart reconciles the ordered durable states; it never parses free text or trusts a returned helper status alone.

Safe Undo uses a distinct exact template schema, `writcraft.snapshot-restore-undo-history-template/v1`, in that same WRCCHRA2 `preparedDelta` section; it is not a sidecar, second artifact, marker extension, or second History store. Its exact fields are `schema`, `id`, `changeSetId`, literal `status == undone`, `appliedAt`, `undoneAt`, ordered `files`, exact Snapshot `provenance`, and `baseHistoryState`. `baseHistoryState` exact fields are literal `exists == true` and the 64-lowercase-hex digest `SHA256(0x01 || exact raw changes.json bytes)`. Every file is the complete sealed Snapshot History v4 file—`path`, `summary`, exact `before|after` base64 states, nullable `createdIdentityDigest`, and non-null `ancestorIdentityDigest`—in the original record order; the complete set is one through 300 and provenance `selectedIds` retains the same count/order. The template is descriptor-exact plain data throughout: accessors, symbols, hidden/named/sparse array entries, extra fields, cross-kind ordinary restore templates, reordered or foreign records, and raw-base formatting drift fail without invoking getters.

The undo template digest is the repository section 3.1.4 authority: `SHA256(UTF8("writcraft-digest/v1") || 0x00 || UTF8("writcraft.snapshot-restore-undo-history-template/v1") || 0x00 || UTF8(canonicalJson(full exact template)))`, exposed with the `sha256:` prefix. WRCCHRA2 stores those canonical template bytes as the existing preparedDelta bytes and retains the existing 32 MiB section limit and 384 MiB artifact cap. Artifact v2 inspection distinguishes the ordinary restore and Safe Undo template schemas before materialization; artifact v1 and the already-frozen ordinary restore template remain byte-compatible. To materialize after restart, Main parses and validates the artifact's exact raw base History, reproduces `baseHistoryState.digest`, finds the exact still-`applied` Snapshot record by `id`, and requires its change-set identity, applied time, complete files, ancestor/created identities and provenance to equal the template. It changes only that record to `status == undone`, appends the frozen `undoneAt`, recomputes record integrity, and pretty-serializes the complete changes/v4 document with its terminal newline. `preparedHistoryDigest` is `SHA256(0x01 || those exact prepared History bytes)`. No current clock, live History scan, current file bytes, or caller-supplied replacement record may participate in restart reconstruction.

The Safe Undo mainline History commit is legal only from exact `QUARANTINED` while `publicMarkdownUndoSettlement` is absent; a persisted B settlement selects the mutually exclusive restore branch and can never be reinterpreted as History authority. Before creating the History temp file, Main holds and revalidates the exact raw base History, marker whole bytes/inode, artifact/template, project/root/recovery/ancestor authority and a fresh complete Q `RECONCILE_UNDO == COMMITTED` token set. The History writer uses the materialized artifact result only, with exact-base CAS, temp write, file fsync, atomic rename and parent fsync. A failure before rename leaves base History plus `QUARANTINED`; rename-committed/parent-fsync response loss is recognized only when the exact prepared raw digest is visible and the same parent is re-fsynced. Before marker CAS, Main holds the exact prepared History file/parent, repeats fresh Q reconciliation, reproduces the complete native/root/recovery authority and requires byte-identical token truth, then advances only `QUARANTINED → HISTORY_COMMITTED`. Marker rename or recovery-directory-fsync response loss restarts from the same artifact and exact prepared History and converges that marker transition without rewriting History. Seeing the committed marker bytes is not durability acknowledgement: every `HISTORY_COMMITTED` restart must descriptor-hold the exact marker/recovery directory and public ancestor set, revalidate root/project/artifact/prepared History, fsync that same recovery-directory fd, then re-open and compare the directory and marker before returning the phase. A failed or repeatedly failed fsync keeps the marker locked at `HISTORY_COMMITTED`; same-byte marker replacement and project-root or recovery-directory replacement remain untouched and fail closed. Foreign/minified raw base, a legally re-signed ancestor/provenance change, Q `UNKNOWN|UNCOMMITTED`, settlement presence, or marker/artifact/root/recovery drift advances nowhere. This layer never invokes B, D or A and never terminalizes or cleans the artifact/marker.

Safe Undo's descriptor/no-clobber quarantine implementation may be reused as a low-level native primitive, but its Q/R/B/D/A records are not rollback-create authority. Safe Undo is bound to `snapshot_restore_undo + PRECREATE + CREATED`, `RESTORE_QUARANTINE` restores a public leaf, and `FINALIZE_UNDO` requires committed undone History. Rollback-create is bound to `snapshot_restore + CREATED_RECEIPT + MISSING`, must prove existing `UNCOMMITTED` plus exact base History, and removes only receipt-owned just-created leaves. It therefore requires a separately frozen `ROLLBACK_CREATE` schema/record/command domain while retaining this same marker/artifact; no Safe Undo receipt relabeling, path unlink, generic recovery writer, or second marker is permitted. Until that native domain and the formal existing-file executor are independently signed, mixed restore remains stop-before-native with `SNAPSHOT_RESTORE_MIXED_SELECTION_UNAVAILABLE`.

The phase validator is only a structural/CAS gate. It does not accept a caller's claimed `COMMITTED|UNCOMMITTED|UNKNOWN`, synthesize either receipt-set digest, or treat a matching digest string as proof that History is still at base. The later existing-file and rollback-create authority schemas must derive the complete ordered `EXISTING` and `MISSING` subsets from this same parent binding and must reproduce the held-fd exact raw History base before their first mutation and again at their commit/reconcile boundary.

The existing transaction boundary is correspondingly frozen as four Main-only steps. `prepareSnapshotRestore`/`prepareSnapshotRestoreUndo` produce and persist `PRECREATE` authority; the native adapter returns typed creation/quarantine receipts; reconciliation CAS-advances the same marker; History commit consumes only the receipt-derived prepared state; post-History finalization consumes the same receipt and advances the mainline marker to `FINALIZED`, while a pre-History Safe Undo abort may consume only the formal B result and advance `QUARANTINED` to terminal `RESTORED`. Renderer never calls a phase step and never supplies path, bytes, identity, receipt, output location, or phase claim. Existing `execute(prepared)` remains the ordinary apply/review/undo route; Snapshot must not be squeezed through its one-shot `prepared.execute()` callback once phase execution is enabled.

## 2. State and authority matrix

The durable state is `applying` or `terminal`. Terminal outcomes are:

- `applied`, `reviewed`, or `undone`: every file and exact History state match the prepared transaction;
- `zero_write_error`: every file and History match the operation-before state;
- `committed_warning`: all manuscript files match operation-after but History remains at operation-before;
- `manual_recovery`: files are mixed/unknown, History contradicts files, or any authority cannot be proven.

Main never trusts the returned status from a write helper alone. It authoritatively rereads every affected file and the complete History after success, failure, thrown error, restart, or response loss.

For Snapshot restore, restart opens the artifact with `O_NOFOLLOW`, verifies held-fd inode/type/link count, exact byte length and whole-file SHA-256, parses from that same fd, and repeats `fstat` after the read. Each streamed record must match the compact control path/revision/existence binding. Existing leaves bind their normal authority immediately. A missing leaf binds null created identity only in `PRECREATE`; from `CREATED_RECEIPT` onward, the marker phase item and native receipt must bind the exact created identity. Base History binds the exact raw on-disk bytes captured through a held no-follow fd, not a pretty-printed normalization; therefore minified but valid `changes/v4` remains exact base authority. Prepared History binds the deterministic receipt-materialized state. Current History uses the same existence-prefixed raw-byte streaming digest with before/after fd identity checks. Restart does not need Renderer state or a replayed capability.

Phase reconciliation is exact: restore `PRECREATE` with no created receipt and no created inode is zero-write; a valid created receipt plus its exact inode may advance to `CREATED_RECEIPT`; a receipt without the exact inode, an inode without a durable receipt, mixed receipt sets, or foreign ancestor/content state is manual recovery. All-missing `CREATED_RECEIPT` with exact base History may finish receipt-derived History. Mixed `CREATED_RECEIPT` may only reconcile the formal existing executor: exact `COMMITTED` advances to `EXISTING_COMMITTED`, exact `UNCOMMITTED` plus exact base History may begin rollback-create, and `UNKNOWN` stays locked. `EXISTING_COMMITTED` may only finish History; it never rolls back committed existing writes through a generic writer. Rollback-create may quarantine/finalize only receipt-owned created inodes and may publish `ROLLED_BACK` only after all selected files and exact raw History prove operation-before. If current History already equals the receipt-derived digest, restart advances to `HISTORY_COMMITTED` only from its allowed predecessor. Safe Undo `PRECREATE` may advance only from a complete exact Q/R `COMMITTED`; `QUARANTINED` with exact base History may either commit prepared undone History or run B. A B `COMMITTED` final record plus exact restored public authorities and unchanged base History advances to terminal `RESTORED`; B `UNCOMMITTED|UNKNOWN` advances nowhere. Once History equals prepared, B is forbidden and only D may reach `FINALIZED`.

`rollback_failed` and `history_failed_rollback_failed` are uncertain outcomes. They consume/isolate the original capability and may never return as ordinary retryable failures.

## 3. Recovery choices

While any marker exists, autosave, file lifecycle operations, AI mutations, Changes apply, History undo, migration writes, Graph correction writes, and Inline apply are blocked. Read-only file/tree/History access and recovery IPC remain available.

For `applied`, `reviewed`, `undone`, or `zero_write_error`, Renderer reloads authoritative tree, current file when affected, and History, then exact-clears the marker. A missing response follows this same query/reload/clear path.

`committed_warning` and `manual_recovery` keep the project blocked and show affected relative paths plus two explicit Main-owned actions:

1. **Restore operation-before** — write every affected file to the sealed before content and restore the sealed base History.
2. **Keep operation-after** — write every affected file to the sealed after content and commit the prepared History.

Main permits either action only when every current file is still exactly the sealed before or after revision and current History is exactly the sealed base or prepared state. A third file revision, foreign History state, corrupt marker, watcher degradation, or recovery write failure keeps the marker and project locked. Recovery actions are idempotent and never infer content from Renderer state.

The generic `restore_before` / `keep_after` writer is forbidden for both Snapshot kinds. It cannot safely create a missing leaf or delete a created leaf from path/content alone, so Snapshot markers expose no generic recovery actions and return `SNAPSHOT_RESTORE_SAFE_RECOVERY_REQUIRED` if that route is attempted.

`snapshot_restore_undo` uses the same marker/artifact and the phase extension above. The native resolver must move the exact created inode into private unpredictable quarantine with no-clobber semantics and revalidate trusted root, full public ancestor chain, leaf inode/size/content, and `createdIdentityDigest`; durably publish the hash-bound quarantine receipt; let Main CAS-commit the prepared `undone` History; then unlink and fsync only that quarantined inode and durably publish the final receipt. A crash or explicit abort before History commit retains the exact inode for receipt-driven B restoration; only a B `COMMITTED` final record plus exact base History may publish terminal `RESTORED`. A crash after History commit finishes deletion from the same receipt and can never call B. A one-shot unlink callback, path unlink, generic recovery action, backward phase rewrite, or marking History undone before quarantine authority is forbidden. Until these phases are implemented, the existing `SNAPSHOT_RESTORE_QUARANTINE_UNAVAILABLE` pre-marker gate remains authoritative and cannot produce `committed_warning`.

## 4. Lifecycle

1. Main validates project, dependency, decision, History capacity, and recovery absence.
2. Main prepares the exact History mutation and atomically writes the `applying` marker.
3. After marker persistence succeeds and before the first manuscript/History write, a Main-owned begin callback consumes or isolates the pending apply capability. Callback failure is zero-write and terminal; it cannot be skipped or moved after the first write.
4. Main performs apply/review/undo, then classifies by authoritative files plus History.
5. Main persists the terminal marker before returning any result.
6. Renderer blocks mutation, reloads Main authority, exact-clears safe terminal outcomes, and only then resumes editing.
7. On navigation, crash, restart, malformed response, or IPC loss, project bootstrap queries and reconciles the marker before opening editable content.

For Snapshot restore, artifact creation atomically claims its final basename with `O_CREAT|O_EXCL`, then fsyncs the held file and directory before marker publication. Production JavaScript never path-unlinks that name on success, rollback, publication failure, or clear. Marker-publication rollback and terminal-clear cleanup are exclusively delegated to the injected native exact-lifecycle adapter described above. Native cleanup durably publishes immutable control, quarantine-proof, and terminal-receipt records; the proof binds the exact control digest, basename, quarantine, SHA-256, and byte length, while the receipt binds that same tuple plus the exact proof digest. ACK treats the canonical control as authority, reconstructs the only acceptable proof and receipt bytes, verifies the token receipt digest and deterministic record names, and only then identity-checks and unlinks those exact bytes in receipt→proof→control order. Receipt-absent retry reconstructs the relation from remaining control/proof; an independently self-hashed late replacement is foreign and is never removed. Cleanup moves the exact source to a private unpredictable `.changes-history-cleanup.<128-bit-random>` name with `RENAME_EXCL`, reopens and rehashes that exact inode, then unlinks and fsyncs. Cleanup response loss and the `open→rename`, `rename→reopen`, `reopen→unlink`, and `unlink→directory-fsync` windows retry from those records into `COMMITTED|UNCOMMITTED|UNKNOWN`. If exact removal cannot be proved, the remaining name or record is durable recovery residue, not something Main may guess away.

The public-Markdown adapter is a separate native helper from Snapshot bundle storage and artifact cleanup, but it is scoped by the same Changes/History operation and recovery directory. On startup Main passes a read-only trusted filesystem-root fd plus one bounded canonical root bind record; later commands contain only the operation ID, relative Markdown path, immutable artifact/phase digests, expected ancestor/content/identity bindings, and receipt tokens. The helper descriptor-walks every external component with no-follow `openat` and rewalks the complete root chain before and after each mutation.

For missing restore, native `CREATE` opens the already-validated parent descriptor, uses `O_CREAT|O_EXCL|O_NOFOLLOW` and exact private mode, writes only the artifact-bound bytes through that returned fd, fsyncs the file, captures public ancestor/leaf identity and content hash from held descriptors, fsyncs the public parent, rewalks root/ancestors, then durably publishes a receipt in the existing private recovery directory before returning its digests. It must never derive ownership from an after-the-fact path `stat`. For Safe Undo, native `QUARANTINE` descriptor-opens and hashes the exact History-bound leaf, no-clobber moves it to an unpredictable private name, reopens and revalidates the quarantined identity, fsyncs both public parent and private recovery directory, and durably publishes its receipt. `RESTORE_QUARANTINE`, `FINALIZE_CREATE`, `FINALIZE_UNDO`, and `RECONCILE` accept only those exact receipts. Unknown outcome, root/ancestor drift, same-name replacement, content drift, receipt mismatch, scan bound, or durability failure remains fail closed. A same-UID writer already holding an fd remains outside atomic exclusion; before/after identity and content checks detect drift but do not claim to prevent such writes.

#### 4.2.1 WRCCHRJ2 physical bridge amendment (E-3 refreeze)

For the journal-backed route, `E` no longer consumes a legacy JSON marker as its
cross-process marker authority. The sole physical bridge is the existing
owner-only `WRCCHRJ2` permanent journal defined in section 4.6. Legacy
`changes-history-transaction.json` remains read-only migration evidence for
legacy compatibility; it is not an E request input, a held-fd publication
anchor, a CAS token, or a source from which Main may recapture current
identities. No sidecar, second marker, second journal, index, scanner, or
parallel publication record is introduced.

The journal-backed E request and its held descriptors must bind one exact
current physical head before helper spawn. The binding is descriptor-exact and
contains, at minimum, the full journal-file identity (regular owner-only
`0600`, one link, `dev`, `ino`, `uid`, `mode`, `nlink`, `size`, `mtimeNs`,
`ctimeNs`, and complete-file SHA-256), trusted-root and recovery-directory
identities, the logical `slot`, `journalId`, decimal `generation`, exact
`previousValueDigest`, exact current `valueDigest`, complete WRCCHRJ2 frame
byte length/SHA-256 and payload byte length/SHA-256, plus the canonical
`activeMarker` slice offset/length and `activeMarkerDigest`. The outer frame
head and nested VALUE must agree byte-for-byte; an expected head is not
replaced by a digest-only or legacy-marker claim. The request still carries the
complete original E authority, artifact/History bindings, ordered items and
held artifact/root/recovery descriptors; those bindings are joined to this
single journal head, not recaptured from public paths.

The required E-to-CAS sequence is frozen as follows: (1) before E, Main reads
the exact WRCCHRJ2 head and validates an ACTIVE `CREATED_RECEIPT` marker slice,
the complete original authority, and absence of `existingTerminalPublication`;
(2) after E returns a complete terminal, Main reopens the journal file
descriptor-relative and rechecks its full identity, root/recovery identities,
slot/frame/head, payload bytes, active-marker slice and digest, together with
the exact control/apply/public/History authority; (3) only then it builds the
next VALUE and performs one APPEND CAS to the inactive slot with exact
`generation + 1`, `previousValueDigest == old.valueDigest`, and the stored
`existingTerminalPublication`; (4) the APPEND implementation fsyncs the frame
and journal file, reopens the journal basename, and reproduces the new physical
head and full journal-file identity; (5) before returning or advancing the
phase, Main repeats the journal/root/recovery, formal-record, public-leaf,
artifact and raw-History checks, including the exact post-commit cleanup
state. Any failure after a helper mutation but before this complete proof is
`UNKNOWN`/manual and retains the journal and all residue.

exact `READ` constrained to the old/new expected heads. An exact old head with
no publication proves that the CAS was not observed; an exact new head with
the stored `existingTerminalPublication` proves the CAS and may be consumed by
fresh R; a missing, conflicting, stale, or physically ambiguous head is
manual `UNKNOWN`. Main must never replay E, infer a commit from visible
control/apply bytes, or rebuild a publication from current inode/stat data.

descriptor-exact identities; same-byte/new-inode, same-inode rewrite, journal

An `E|R` result has only three states. `COMMITTED` carries one descriptor-exact terminal receipt containing every complete per-item apply token in parent order, unique final leaf identities, the exact after content per item, an aggregate receipt-set digest and terminal self digest. `UNCOMMITTED` carries one terminal receipt containing, for every existing item, its optional complete apply token plus mandatory complete rollback token, unique final leaf identity, exact before content, the same base-History digest, aggregate receipt-set digest, terminal self digest, and recovery-directory fsync truth. When both tokens name an apply, their complete apply authority—including control/apply basenames and digests, after-leaf identity, and both publication identities with dev/ino/size/mtime/ctime/content hash—must be canonically identical; matching only `applyReceiptDigest` is insufficient. It means **all** existing leaves and exact raw History equal operation-before; a partial rollback cannot be published as `UNCOMMITTED`. `UNKNOWN` carries no receipt/token and only stable `EXISTING_RESTORE_UNKNOWN`; arbitrary error strings, OS errors, paths, bodies, partial receipt sets, mixed states, or a receipt belonging to the other command/operation are rejected and leave `CREATED_RECEIPT` locked.

The native `E|R` response uses one bounded ASCII line grammar after the startup `P\tOK` bind. The exact result header carries command, state, operation/request digests, the seven terminal authority digests, exact item count and nullable stable error code. Each `COMMITTED` item is one `T` line in parent order and repeats selected ID, final content/leaf digests, deterministic control/apply names and digests, plus the complete ten-field object identity of both formal records. The parser reconstructs the apply receipt, both private identities, token, receipt set and terminal receipt from those fields and accepts the response only if every reconstructed value equals the header and original authority. Each item line is capped at 2,048 bytes; the complete response is capped at 768 KiB, which closes over 300 items plus two maximum header lines. Duplicate, extra, reordered, cross-command, over-budget or partially valid lines fail closed. This wire currently freezes `COMMITTED` and `UNKNOWN`; `UNCOMMITTED` wire is not enabled until the rollback-token slice is independently frozen.

`V` is a fresh exact terminal recheck, not a status echo. Its request repeats the complete original authority and complete terminal receipt. It descriptor-reopens every control/apply/rollback record, public ancestor and final leaf, reproduces record bytes/digests/names/order and exact terminal content/History state, then returns the same `COMMITTED|UNCOMMITTED` terminal digest or `UNKNOWN`. Only verified `COMMITTED` may supply the phase's `existingReceiptSetDigest` and advance to `EXISTING_COMMITTED`; only verified `UNCOMMITTED` may authorize the separately frozen rollback-create branch. A transport failure or malformed result after `E` is attempted requires fresh `R` and, when a terminal receipt appears, `V`; it never repeats `E` or falls back to a one-shot callback.

`F` deterministically publishes `.changes-history-native-existing-final.<64 lowercase hex>`. The final record exact fields bind operation/request, terminal state, terminal and receipt-set digests, item count, recovery-directory fsync truth, and self digest. `COMMITTED` final result additionally binds the complete publication-time private record identity; `UNKNOWN` carries neither record nor identity. ACK repeats the final basename/digest/identity and the exact marker-phase digest that consumed this terminal authority. It reopens only the same owner-only one-link final/control/receipt records, reproduces their canonical bytes and publication identities, exact-removes them through private no-clobber quarantine/reopen/fsync, and is idempotent only for that same complete authority. A same-byte replacement, same-inode rewrite, moved/duplicate/partial/foreign record, wrong marker phase, or missing independent reconciliation is `UNKNOWN` and remains untouched. `reconcileFinalize` must recover the same final record/identity after publish response loss; it cannot invent an ACK from regex-valid digests.

All schemas use the single section 3.1.4 `writcraft-digest/v1` canonical authority. The wire is bounded ASCII tab-delimited: `E` carries complete item metadata with paths encoded as lowercase UTF-8 hex; `R`, `V`, and `F` carry only bounded authority/digests/receipts. One line is at most 16 KiB, one request 4 MiB, one response 256 KiB, a control/apply/rollback record 16 KiB, a final record 4 KiB, and one operation 300 total selected items. Absolute paths, Markdown/History/artifact bytes, output paths and native messages never appear in result or error surfaces. No path-based unlink, free-text parsing, second marker, second History/index/scanner, generic recovery, or Renderer-supplied path/body/receipt is permitted.

Until this schema and the WRCCHRJ2 physical bridge amendment have a separately
reviewed native implementation, production lifecycle adapter and
transaction/reconciliation wiring, mixed selection remains the stable
pre-marker `SNAPSHOT_RESTORE_MIXED_SELECTION_UNAVAILABLE` gate. Pure-schema
green is a contract checkpoint, not production mixed-restore acceptance.

### 4.3 Private `ROLLBACK_CREATE` helper freeze

Mixed restore's failure branch uses a separate private `CREATE_ROLLBACK` domain on the same marker/artifact. It is not Safe Undo with renamed receipts. Its only commands are `Q CREATE_ROLLBACK`, `R CREATE_ROLLBACK`, `D CREATE_ROLLBACK`, and `A CREATE_ROLLBACK`: quarantine, reconcile, delete quarantines, and acknowledge. There is deliberately no `B` restore command because the formal EXISTING executor has already proved every existing leaf and exact raw History are at operation-before; if Q cannot prove either all created leaves quarantined or all of them restored to their exact created state, reconciliation returns `UNKNOWN` and touches nothing.

The private schemas are the domain-separated `writcraft.changes-history-native-rollback-create-{request,authority,held-binding,control,receipt,token,result,settle-request,receipt-set,final-record,settle-result,ack-request,ack-result}/v1`, plus distinct record/final keys. Every authoritative API receives the complete startup root bind, same parent `snapshot_restore` selection, exact original `PRECREATE` phase, exact `CREATED_RECEIPT` phase, original native CREATE request, complete ordered CREATE publications, complete formal EXISTING authority and exact `UNCOMMITTED` terminal receipt. Descriptor-exact validation rejects accessors without invoking getters, Symbols, non-enumerable/unknown fields, sparse arrays, prototype variation, reorder, omission, cross-command, cross-operation and partial authority before spawn or filesystem access.

The held-binding exact fields are `schema`, `markerByteLength`, complete `markerIdentity`, `historyParentIdentityDigest`, literal `baseHistoryExists`, nullable `baseHistoryContentDigest`, and nullable complete `baseHistoryIdentity`. `markerIdentity` is the owner-only one-link `0600` regular file observed from fd 5 and its content SHA-256 equals the whole raw `markerDigest`; its size equals `markerByteLength`. fd 6 is the held owner-safe `.writcraft` History parent directory and reproduces `historyParentIdentityDigest`. If `baseHistoryExists == true`, fd 7 is the held read-only no-follow owner-only one-link `0600` `changes.json`; its full identity, raw content SHA-256 and byte length reproduce `baseHistoryIdentity`, `baseHistoryContentDigest`, and `baseHistoryByteLength`, while native independently hashes the same bytes with the existence prefix to reproduce `baseHistoryDigest`. If `baseHistoryExists == false`, `baseHistoryByteLength == 0`, both nullable fields are null, `baseHistoryDigest == sha256(0x00)`, and fd 7 is the same directory authority as fd 6 so native can prove descriptor-relative absence of `changes.json` before and after the command. fd 4 remains the held immutable artifact. All four fds are supplied to Q/R/D/A; they are access-mode checked and fstat/reopened/path-bound before the first control/public mutation, immediately before any public rename or quarantine deletion, and again after private publication/fsync and before returning. A same-byte new inode, same-inode rewrite, parent replacement, fd/path disagreement, writable fd, link-count/owner/mode drift, or any unavailable fd is `UNKNOWN` before further mutation; path reads and generic directory scans cannot replace these descriptors.

The request exact fields are `schema`, `operationId`, whole raw `markerDigest`, `markerByteLength`, `markerIdentityDigest`, artifact digest/identity/length, root/recovery identity digests, original `createPrecreatePhaseDigest`, section 3.1.4 `createdReceiptPhaseDigest`, full `selectionDigest`, non-null `preparedHistoryDigest`, exact `originalPrecreateUpdatedAt`, exact `originalCreatedReceiptUpdatedAt`, formal `existingRequestDigest`, EXISTING terminal/receipt-set digests, `historyParentIdentityDigest`, exact raw base-History digest/length/existence/content/identity binding, and ordered `items`. The original PRECREATE time is not inferred from CREATED_RECEIPT and must not be later than the latter. The request must reproduce the same marker/artifact/root/recovery and the same formal EXISTING `UNCOMMITTED` state. Its items equal the complete parent-derived `MISSING` subset in parent order. Each item binds selected ID/path, original CREATE `artifactOffset`, exact Snapshot byte length/content digest, ancestor identity, created leaf identity, deterministic CREATE control/receipt basenames and digests, and the complete publication identities plus canonical wire hashes of both CREATE records. These fields let native rebuild the complete original CREATE request, every CREATE control/receipt canonical byte string, and the exact PRECREATE and `CREATED_RECEIPT` phases; a supplied digest, timestamp or publication identity alone is not authority. A regex-valid receipt, same-byte replacement inode, matching receipt digest with different publication metadata, fabricated created identity, `COMMITTED` EXISTING result, History drift, or mixed/omitted receipt set cannot authorize Q.

Every Q/R/D/A wire repeats one bounded authority header plus the complete ordered EXISTING and MISSING projections; D/A additionally carry the full ordered Q token set, and A carries the exact consuming phase time/digest and final publication identity. The header includes the original CREATE precreate digest, CREATED_RECEIPT prepared-History digest, and lowercase UTF-8 hex of both `originalPrecreateUpdatedAt` and `originalCreatedReceiptUpdatedAt`. Every `E` and `I` line also carries its unique zero-based `parentIndex`; the union must cover exactly `0..selectedCount-1`, while each typed subset remains in parent order. Each `E` line contains the corresponding EXISTING request item and complete `UNCOMMITTED` terminal item: its parent revision is exactly `afterRevision`, plus final before-content/leaf identity, rollback token, nullable apply publication, and complete control/apply/rollback record identities. Each `I` line contains the MISSING request item including `artifactOffset` and complete original CREATE control/receipt publication identities; its parent revision is the 64-hex payload of exact `contentDigest == sha256:<revision>`. Line type fixes `EXISTING|MISSING`. Native must reconstruct the complete mixed parent selection from only these indexed E/I fields, recompute `selectionDigest`, then independently reconstruct and hash the exact PRECREATE and CREATED_RECEIPT phases from their respective timestamps. It must not fill those structures from caller-supplied parent/phase objects or accept the header digests as proof. Therefore it can deterministically rebuild the original CREATE request/publications, existing request digest, terminal receipt-set and terminal receipt, reopen every exact publication record, and reject missing, duplicate, out-of-range or reordered indexes, timestamp forgery, omission/reorder/partial/cross-operation authority without scanning the recovery directory. A digest-only EXISTING or CREATE claim, one-line D/A shortcut, or caller assertion that the upstream terminal is still valid is non-authoritative.

Q publishes one domain-separated control per item, using deterministic `.changes-history-native-rollback-create-{control,receipt}.<64 hex>` names and an unpredictable `.changes-history-native-rollback-create-quarantine.<32 hex>` name. It no-clobber moves only the exact receipt-owned created leaf into the private recovery directory, reopens the quarantine and reproduces created identity/content/ancestor authority, fsyncs the public parent and recovery directory, then publishes a receipt and token bound to complete control/receipt publication identities. There is no path `lstat→unlink`, no generic scan, and no cleanup of an unowned or replaced leaf.

Q/R have exactly three results. `COMMITTED` carries the complete ordered quarantine token set with unique quarantine identities. `UNCOMMITTED` carries no token and is legal only after all controls/quarantines have been exactly reconciled away, every created public leaf again equals its original CREATE publication, both directories are fsynced, formal EXISTING `UNCOMMITTED` still holds and raw History remains exact base. `UNKNOWN` carries no token and only `ROLLBACK_CREATE_UNKNOWN`; it preserves every public/private object and leaves phase `CREATED_RECEIPT` locked. A malformed/missing Q response triggers fresh R, never a second Q or a Safe Undo/generic restore command.

D accepts only the full original authority plus every Q token. Immediately before deleting any quarantine it rewalks root/recovery, reproduces the marker/artifact/CREATE publications, formal EXISTING `UNCOMMITTED`, exact base History and every control/receipt/quarantine identity. It exact-deletes only verified quarantines, fsyncs their directory and publishes a deterministic `.changes-history-native-rollback-create-final.<64 hex>` record containing the aggregate receipt-set digest, item count and both durability truths. Any partial/foreign/replaced record or drift is `UNKNOWN` and remains untouched. Only that final record digest may populate phase `rollbackReceiptDigest` and advance `CREATE_ROLLBACK_QUARANTINED → ROLLED_BACK`.

A requires the exact `ROLLED_BACK` phase that consumed the same EXISTING receipt-set and D final-record digest, plus the final record's complete publication identity. Main/native deterministically rebuild that phase from the original `CREATED_RECEIPT` and complete ordered Q token set: every MISSING item must retain the same selected ID/path/revision/ancestor, created identity, CREATE receipt and prepared-History digest, and its quarantine receipt must equal the corresponding Q token receipt; only the top phase, EXISTING receipt-set and rollback-final digest may advance as frozen. A carries lowercase UTF-8 hex of the new `updatedAt`; native requires a valid canonical timestamp not earlier than `originalCreatedReceiptUpdatedAt`, rebuilds both exact phases and compares their section 3.1.4 digests. Comparing only top-level phase fields or supplied phase digests is forbidden. It reopens and reproduces only the same final/control/receipt records before private no-clobber quarantine/remove/fsync; all already absent is idempotent ACK only for that exact authority. A moved record, same-byte replacement, same-inode rewrite, partial set, different phase or guessed digest is `UNKNOWN` and remains untouched.

All names and digests use section 3.1.4 `writcraft-digest/v1`; the domain never reuses Safe Undo Q/R/D/A names or receipts. Wire tags are literal `Q|R|D|A` plus `CREATE_ROLLBACK`; there is no B frame. Paths are lowercase UTF-8 hex. Budgets are 300 total selected items, 16 KiB per line/record, 4 MiB request, **512 KiB ROLLBACK_CREATE response**, and 4 KiB final record, with absolute paths, Markdown/History/artifact bodies, output locations, native messages and raw OS errors forbidden. The 512 KiB cap is domain-specific: CREATE, Safe Undo and every other existing native response remain capped at 256 KiB. Until native implementation, production lifecycle wiring and independent review exist, mixed restore remains `SNAPSHOT_RESTORE_MIXED_SELECTION_UNAVAILABLE` before marker or native mutation.

This subsection freezes only the private Safe Undo protocol required before `SNAPSHOT_RESTORE_QUARANTINE_UNAVAILABLE` may be removed. It reuses the same public-Markdown helper, trusted root bind, held recovery directory and parent Snapshot Changes/History marker/artifact; it does not create another helper, recovery directory, History store, public schema, scanner or path-delete fallback. Until native code and a scoped Main adapter independently satisfy this freeze, the pre-marker gate remains authoritative.

The schemas are `writcraft.changes-history-native-undo-request/v1`, `writcraft.changes-history-native-undo-control/v1`, `writcraft.changes-history-native-undo-receipt/v1`, `writcraft.changes-history-native-undo-token/v1`, `writcraft.changes-history-native-undo-result/v1`, `writcraft.changes-history-native-undo-settle-request/v1`, `writcraft.changes-history-native-undo-receipt-set/v1`, `writcraft.changes-history-native-undo-final-record/v1`, `writcraft.changes-history-native-undo-settle-result/v1`, `writcraft.changes-history-native-undo-ack-request/v1`, and `writcraft.changes-history-native-undo-ack-result/v1`. Accessors, symbols, non-enumerable/inherited/extra keys, prototype changes, sparse or named array entries, unsafe Unicode, C0 controls and unpaired UTF-16 surrogates fail before wire encoding or mutation.

Every authoritative API receives one complete original authority consisting of the exact root bind, parent `snapshot_restore_undo` selection, exact `PRECREATE` phase and undo request. The undo request exact fields are `schema`, `operationId`, `artifactDigest`, `artifactIdentityDigest`, `artifactByteLength`, `rootIdentityDigest`, `recoveryIdentityDigest`, `precreatePhaseDigest`, `selectionDigest`, `preparedHistoryDigest`, and ordered `items`. It must bind the startup root/recovery digests, immutable held-artifact identity/length/digest, section 3.1.4 digest of the exact `PRECREATE` phase, complete parent selection digest and prepared-undone-History digest. Its items must equal the complete parent-derived ordered `CREATED` subset—never a caller-selected subset. Each item exact fields are `selectedId`, relative NFC Markdown `path`, `byteLength`, `contentDigest == sha256:<afterRevision>`, `ancestorIdentityDigest`, and the non-null `createdIdentityDigest` sealed by the applied Snapshot History. Omission, insertion of `EXISTING`, reorder, duplicate ID/path/created identity, cross-parent item, project/root/artifact/History/phase drift or more than 300 items fails closed.

For each item, a control exact fields are `schema`, every operation/root/artifact/History/phase/item field required to reconstruct the request relation, and `controlDigest`. Its record-key exact fields are `schema`, `operationId`, `selectedId`, `artifactDigest`, `precreatePhaseDigest`, `selectionDigest`, `preparedHistoryDigest`, and `createdIdentityDigest`. The section 3.1.4 digest suffix determines both `.changes-history-native-undo-control.<64 lowercase hex>` and `.changes-history-native-undo-receipt.<same suffix>`. Before any public rename, native requires the complete deterministic control set to be created by that invocation using no-clobber held fds; any preexisting, partial, moved-only, duplicated, late, exact-looking or foreign set is `UNKNOWN` and remains untouched.

`QUARANTINE` descriptor-opens the exact History-bound public leaf, verifies complete ancestor identity, inode metadata, byte length, whole content digest and `createdIdentityDigest`, then moves only that held inode with no-clobber semantics to a fresh `.changes-history-native-undo-quarantine.<32 lowercase hex>` in the held recovery directory. It reopens that exact quarantine, revalidates identity/content/ancestor and absence of a visible replacement, fsyncs the public parent and recovery directory, and durably publishes a receipt. One receipt exact fields are `schema`, `operationId`, `selectedId`, `controlDigest`, `quarantineBasename`, `createdIdentityDigest`, `quarantineIdentityDigest`, `contentDigest`, `byteLength`, literal true `publicParentFsyncComplete`, literal true `recoveryFsyncComplete`, and `receiptDigest`. The token contains no path or body; a structural token parser is explicitly non-authoritative and cannot encode a mutation or replace the complete bound validator.

`QUARANTINE` and fresh-process `RECONCILE_UNDO` results exact fields are `schema`, mandatory exact `command`, `state`, operation/artifact/precreate/selection/prepared-History digests, ordered `tokens`, and nullable `errorCode`. `COMMITTED` alone carries the complete ordered token set and proves every public name absent, every quarantine/receipt/control exact, and both directory fsyncs. `UNCOMMITTED` carries no tokens and requires every original public inode/content/ancestor exact, every quarantine/receipt absent, exact cleanup of only this invocation's controls, and recovery-directory fsync. `UNKNOWN` carries no tokens and only `PUBLIC_MARKDOWN_NATIVE_UNKNOWN`. Partial or mixed moves/receipts, public and quarantine both present/absent without exact terminal authority, same-inode rewrite, same-byte new inode, foreign record, root/ancestor drift, response loss without exact records, or scan/budget/durability failure is `UNKNOWN`; it never authorizes cleanup. After a missing or malformed `QUARANTINE` response Main destroys that transport and asks a fresh helper to `RECONCILE_UNDO`; it never replays `QUARANTINE`.

Settlement has two command-bound branches using the same complete ordered tokens. `RESTORE_QUARANTINE` is legal only while History remains at the sealed base state and therefore requires literal null `historyCommittedPhaseDigest`; it no-clobber restores each exact quarantined inode to its still-absent public leaf and fsyncs both parents. Its `COMMITTED` final record authorizes only `QUARANTINED → RESTORED`, never a backward rewrite to `PRECREATE` and never an `undone` outcome. `FINALIZE_UNDO` is legal only after Main has durably installed the prepared undone History and requires its exact `HISTORY_COMMITTED` phase digest; it unlinks/fsyncs only the exact quarantined identities and authorizes only `HISTORY_COMMITTED → FINALIZED`. Their common settle-request exact fields are `schema`, exact `command`, `operationId`, `artifactDigest`, `precreatePhaseDigest`, `selectionDigest`, `preparedHistoryDigest`, nullable-by-command `historyCommittedPhaseDigest`, and complete ordered `tokens`. A result is `COMMITTED|UNCOMMITTED|UNKNOWN`; only `COMMITTED` carries both the exact final record and its complete `finalRecordIdentity`, `UNCOMMITTED` carries neither and proves no settlement mutation, and `UNKNOWN` carries neither plus only the stable unknown code. The final identity uses the same descriptor-exact `writcraft.object-identity/v1`, private-mode, single-link, exact-size and canonical-byte hash rules as control/receipt identities. A partial/foreign set is always `UNKNOWN` and untouched; receipt-absent/control-exact is not retry permission.

The receipt-set exact fields are `schema`, operation/artifact/precreate/selection/prepared-History digests and ordered `items`; each item exact fields are `selectedId`, `controlDigest`, `createdIdentityDigest`, `quarantineIdentityDigest`, `receiptDigest`, `controlRecordIdentityDigest`, and `receiptRecordIdentityDigest`. Both identity digests use section 3.1.4 over the complete exact object-identity record, so the receipt-set and terminal name change when any record inode, metadata, timestamp, size or canonical bytes changes. The terminal record exact fields are `schema`, settlement `command`, operation/artifact/precreate/selection/prepared-History digests, nullable-by-command `historyCommittedPhaseDigest`, `receiptSetDigest`, `itemCount`, literal true `publicParentFsyncComplete`, literal true `recoveryFsyncComplete`, and `finalRecordDigest`. Its deterministic basename is `.changes-history-native-undo-final.<suffix>`, where the suffix is the section 3.1.4 digest of the final-key exact fields `schema`, settlement command, operation/artifact/precreate/selection/prepared-History digests, nullable history-committed phase digest and receipt-set digest. `finalRecordDigest` alone populates the phase `finalReceiptDigest`: B binds terminal `RESTORED`, while D binds terminal `FINALIZED`.

Safe Undo B restart authority remains inside the same existing recovery marker as the optional kind-scoped `publicMarkdownUndoSettlement` subrecord; it is not a sidecar, second marker, public IPC schema, or permission to persist a path/body. Its private schema is `writcraft.snapshot-public-markdown-undo-settlement/v1`, capped at 512 KiB canonical JSON. Its exact fields are `schema`, `state == PREPARED|COMMITTED`, literal `command == RESTORE_QUARANTINE`, `operationId`, `undoRequestDigest`, exact `settleRequest`, `settleRequestDigest`, `receiptSetDigest`, deterministic `finalBasename`, deterministic exact `finalRecord`, and nullable-by-state `finalRecordIdentity`. `undoRequestDigest` is the section 3.1.4 digest of the complete reconstructed original `writcraft.changes-history-native-undo-request/v1`; it binds root/recovery, artifact identity/length/digest, PRECREATE, selection, prepared History and the complete ordered CREATED subset without storing the startup canonical root or Markdown paths again. `settleRequest` is the frozen native B request and therefore retains every complete ordered Q token, including random quarantine basename and full control/receipt publication identities. The other digests, basename and final record must reproduce exactly from that original authority and request; `PREPARED` requires literal null `finalRecordIdentity`, while `COMMITTED` requires the complete descriptor-exact identity from formal B `COMMITTED` truth. Extra, accessor, hidden, cross-command, reordered, stale-request or partial-final authority fails before native mutation. The maximum legal 300-item Unicode fixture is 454,311 canonical bytes; 301 items and any authority above 512 KiB are rejected.

The marker nullability/transition is one-way and is authorized by one descriptor-exact marker-transition validator, not by separately validating two snapshots. `PRECREATE`, the History-committed/D branch and `FINALIZED` require this B-only subrecord to be null. `QUARANTINED` initially permits null; author-request or formal pre-History abort first CAS-publishes only `PREPARED` while exact raw History still equals base and fresh Q reconciliation still proves the complete committed token set. The only first transition is exact `QUARANTINED + null → QUARANTINED + PREPARED` with the phase record byte-for-byte stable. B is forbidden until that marker CAS is durable, so a persist failure makes zero B calls. A B response loss may retry only the identical stored request. One B advance invokes that exact wire at most three times: the primary attempt, at most one response-loss/`UNKNOWN` reconciliation retry, and one immediate pre-marker-CAS proof; none is a new mutation authority. Formal B `COMMITTED` atomically CAS-advances exact `QUARANTINED + PREPARED → RESTORED + COMMITTED`; both the phase transition and the settlement `PREPARED → COMMITTED` transition must validate together. `RESTORED` requires that exact subrecord, the same ordered quarantine receipt digests and `phase.finalReceiptDigest == settlement.finalRecord.finalRecordDigest`; only an exact stable `RESTORED + COMMITTED` replay is permitted afterward. A surviving marker may never drop, rewrite, skip, cross phases or move `PREPARED|COMMITTED` back to null. Restart reconstructs the original native authority from the held marker/artifact, validates it against `undoRequestDigest`, and uses the stored request/final record/final identity to retry the same A; it never asks the now-`UNKNOWN` Q reconciliation to recreate tokens. One terminalization likewise invokes the same exact A wire at most three times: primary, at most one response-loss/`UNKNOWN` retry, and one immediate pre-terminal-marker-CAS proof. Before and after every native callback Main revalidates root/project, held marker whole bytes/identity, artifact, exact raw base History and phase/settlement authority. Only A `ACKED`, production exact artifact cleanup and production exact marker clear remove this authority by removing the marker itself. `UNKNOWN`, missing cleanup adapters, foreign History/root/artifact/marker/final identity, or partial ACK retains `RESTORED` plus the complete settlement authority and performs no path cleanup.

Safe Undo D restart authority is a separate optional kind-scoped `publicMarkdownUndoFinalization` subrecord inside that same recovery marker. It is not the B settlement, a sidecar, a second recovery file, a public IPC schema, or permission to retain an absolute path or body. Its private schema is `writcraft.snapshot-public-markdown-undo-finalization/v1`, capped at 512 KiB canonical JSON. Its exact fields are `schema`, `state == PREPARED|COMMITTED`, literal `command == FINALIZE_UNDO`, `operationId`, `undoRequestDigest`, exact `historyCommittedPhaseDigest`, exact `settleRequest`, `settleRequestDigest`, `receiptSetDigest`, deterministic `finalBasename`, deterministic exact `finalRecord`, nullable-by-state `finalRecordIdentity`, nullable-by-state exact `ackRequest`, and nullable-by-state `ackRequestDigest`. `undoRequestDigest` and the complete ordered D tokens retain the same original Q publication identities as the B domain, but the command, non-null History-committed phase digest, terminal name, final record, and A authority are independently rederived under `FINALIZE_UNDO`. `PREPARED` requires literal null for the last three fields. `COMMITTED` requires the exact D-published full final-record identity, the complete command-bound A request, and its section 3.1.4 digest. The accepted 300-item maximum-Unicode fixture is 454,582 canonical bytes in `PREPARED` and 455,531 bytes in `COMMITTED`; both remain below 512 KiB. A 301st item, an accessor/extra/hidden field, reordered token, cross-command record, stale phase/request digest, partial final identity or independently forged A request is rejected before native mutation.

D is forbidden until an exact marker CAS durably advances `HISTORY_COMMITTED + publicMarkdownUndoFinalization absent → the same byte-for-byte HISTORY_COMMITTED phase + PREPARED`; that CAS retains the complete fresh Q token/publication set and deterministic D request before the first destructive D call. Formal D `COMMITTED` alone may atomically advance `HISTORY_COMMITTED + PREPARED → FINALIZED + COMMITTED`, with `phase.finalReceiptDigest == finalization.finalRecord.finalRecordDigest`; `FINALIZED` keeps the original `HISTORY_COMMITTED.updatedAt` so its exact phase digest and D/A wire remain reproducible. Only an exact stable `FINALIZED + COMMITTED` replay is accepted. One descriptor-exact marker-transition validator checks previous and next phase, B settlement and D finalization together: a surviving marker cannot drop, rewrite, skip or replace either authority, and B settlement must remain absent throughout the D branch. A response loss or process restart uses the marker's stored D request, final record, full final identity and exact A request; it never asks fresh D or Q to guess already-removed identities. `UNKNOWN`, `UNCOMMITTED`, malformed output, missing cleanup adapters, root/recovery/project/artifact/History/marker drift, or partial/foreign private records leaves the prior marker and artifact locked and performs no B call or path cleanup.

After exact A `ACKED`, the same surviving marker retains `FINALIZED + COMMITTED` while it becomes terminal `undone` and while production artifact cleanup persists its formal token. The D finalization subrecord is never nulled or rewritten in a surviving marker; it disappears only when the exact marker itself is successfully cleared. Consequently A committed-response-loss is restartable from the stored full authority even when every native control, receipt, quarantine and final record is already absent. Artifact cleanup response loss restarts only from its persisted cleanup token, and marker-clear response loss restarts only through its formal native reconcile/ACK records. Until A, artifact cleanup and marker clear each prove their own exact terminal truth, `FINALIZED` remains the authoritative recovery lock.

Exact `ACK` receives the complete original authority, settlement request, terminal record and the exact `finalRecordIdentity` published by the committed settlement; its request exact fields are `schema`, settlement `command`, `operationId`, deterministic `finalBasename`, `finalRecordDigest`, and that complete identity. It rederives every control, quarantine receipt, receipt-set and final byte and requires the current records to equal the originally published full identities before it may remove only exact private records through no-clobber quarantine/reopen/identity checks and recovery-directory fsync. A same-byte new inode, same-inode rewrite, metadata/timestamp drift, record replacement or moved-only record is not legitimized by a matching record digest. ### 4.6 Permanent marker value journal amendment (Stage A freeze)

This subsection freezes the replacement authority required before new rollback-create or Safe Undo native publication can be signed. It supersedes terminal marker unlink/republication in section 4.5 for the new route, while section 4.5 remains migration-only compatibility authority for a legacy active JSON marker already on disk. The fixed private basename remains `changes-history-transaction.json`; no second marker, sidecar, recovery directory, scanner, public schema or path-delete fallback is introduced. Once initialized, the marker is a permanent value-authority journal and terminal cleanup advances it to `IDLE`; Main/native never unlink, quarantine, republish or infer authority from absence of that journal.

The physical journal is one owner-only `0600`, one-link regular file beneath the same descriptor-bound owner-only `0700` recovery directory. It has two fixed logical slots `A|B`. Each valid slot carries one canonical `writcraft.changes-history-marker-journal-value/v1` payload and a bounded physical `WRCCHRJ2` frame header whose exact fields are magic, slot, journal ID, unsigned 64-bit decimal generation, exact UTF-8 payload byte length, section 3.1.4 `valueDigest`, nullable-as-`-` `previousValueDigest`, and SHA-256 of the complete payload including its one LF. These duplicated outer fields are physical CAS authority: native can validate a head/predecessor chain without parsing nested business JSON. A writer opens the current basename no-follow read/write, reproduces the trusted-root/project/recovery chain and the unique current slot, requires the exact preceding journal ID/generation/value digest, writes only the inactive payload and fsyncs it, installs its commit header and fsyncs the same file, then reopens the basename and reproduces the new logical head before returning. A single valid slot is accepted only when a descriptor-exact `writcraft.changes-history-marker-journal-head/v1` expected-head authority reproduces its journal ID, generation and value digest; absent that expected head, one invalid slot is corruption rather than assumed inactive/torn proof. When both slots are valid and adjacent, native requires matching journal ID, exactly old generation + 1 and exact `previousValueDigest == old.valueDigest`; after native READ, Main parses the returned canonical business values and runs the complete logical marker transition validator over older→newer before consuming their authority. Equal-generation disagreement, an invalid physical predecessor chain, both slots invalid, overflow, invalid UTF-8, extra bytes, root/recovery drift, or a stale/different logical head is manual recovery. Non-canonical or invalid nested business JSON is independently rejected by Main and never becomes transaction authority. Slot reuse is bounded; the logical payload cap is 96 MiB and the header cap is 512 bytes.

The production physical-CAS collaborator uses the existing `writcraft.changes-history-native-root-bind/v1` startup record on trusted filesystem-root fd 3; that one startup bind is the only place an absolute canonical project root may appear, hex-encoded exactly as already frozen in section 3.1. No later command, result or error contains a path, body, output location, native message or raw OS error. Native independently walks from fd 3 with no-follow descriptor-relative opens through the bound project, `.writcraft`, `recovery`, and fixed journal basename, and reproduces the root/project/recovery identities before and after every read, fsync and logical commit. Root mode `0755` is valid; `.writcraft` and `recovery` remain same-owner exact `0700`. The permanent journal is opened `O_RDWR|O_NOFOLLOW`; initialization alone adds `O_CREAT|O_EXCL`, then enforces owner `0600`, regular-file type and `nlink=1`. A complete new journal inode that reproduces the exact current logical head and valid predecessor is value-equivalent as frozen below; root, private and recovery directories are never clone-equivalent.

The private binary command schema is `writcraft.changes-history-marker-journal-native-{discover|init|read|append}-request/v1`. Main descriptor-exact validates the complete business values, requires generation-zero IDLE before encoding INIT, and runs `assertTransition(previousValue, nextValue)` before encoding APPEND. Its derived `writcraft.changes-history-marker-journal-native-request-authority/v1` exact preimage is `schema`, `command == DISCOVER|INIT|READ|APPEND`, ordered `expectedHeads`, and nullable `nextFrameSha256`; its mandatory `requestDigest` is exactly `evidence-delivery-schema.digestObject(schema, object)` with the section 3.1.4 `writcraft-digest/v1` domain, never a bare SHA of canonical JSON. READ has one exact allowed head, or the ordered adjacent old/next pair used only for response-loss reconciliation, and no payload. APPEND has the exact old and next heads plus the complete next inactive-slot frame; the full previous value stays in Main authority and is not duplicated on the wire. The exact command envelopes are `WRCCHJN2<TAB>DISCOVER<TAB>requestDigest<LF>`, `WRCCHJN2<TAB>INIT<TAB>requestDigest<TAB>journalId<TAB>generation<TAB>valueDigest<TAB>frameBytes<TAB>frameSha256<LF><frame>`, `WRCCHJN2<TAB>READ<TAB>requestDigest<TAB>headCount<TAB>{journalId<TAB>generation<TAB>valueDigest}...<LF>`, and `WRCCHJN2<TAB>APPEND<TAB>requestDigest<TAB>{old head}<TAB>{next head}<TAB>frameBytes<TAB>frameSha256<LF><frame>`. Fields are interpreted by frozen schema key order rather than caller insertion order; every object/array is descriptor-first, exact, plain and dense. Decimal spelling, lowercase digests, declared lengths and exact EOF are immutable; accessors, extras, invalid UTF-8, literal NUL, overflow, trailing bytes and cross-command/request authority fail before mutation.

The domain bridge remains separate from the legacy CREATE v1 result. `createRequestDigest(request)` is the section 3.1.4 digest of the descriptor-validated complete `writcraft.changes-history-native-create-request/v1`. `buildPreparedCreatePublication(request)` is the only PREPARED authority and binds that request digest plus the exact PRECREATE phase digest. A new marker inode containing the complete same current journal value and valid predecessor slot is value-equivalent; code does not delete it merely because its inode changed. A stale generation, different bytes, broken predecessor or different journal ID is foreign and remains untouched with the project locked. The exact mutation subrecord is `writcraft.changes-history-native-publication-mutation/v1` with `state == UNARMED|ARMED|COMMITTED`, nullable exact source-identity digest, nullable unpredictable private basename, and literal directory-fsync truth. `UNARMED` has no source/name and false fsync; `ARMED` binds both and remains false; `COMMITTED` retains both and requires true. It never moves backward or skips. `PREPARED` has no record and an unarmed mutation. Top-level `ARMED` has at least one exact record or armed mutation, permits record state only `ARMED|PUBLISHED`, and may remain `ARMED` while one boundary advances; it can never begin cleanup or claim a newly appended record as already published. Top-level `COMMITTED` requires a non-empty immutable record set in which every record is exactly `PUBLISHED`, plus the intended public/quarantine mutation and its directory fsync committed. Record cleanup begins only with the subsequent top-level `ACK_PREPARED`, which permits only `CLEANUP_ARMED|REMOVED`; `ACK_COMMITTED` requires every record exactly `REMOVED`. Ordinary missing/malformed/timeout responses after `ARMED` restart from this stored identity and converge without replaying a destructive first command or recapturing current inode authority.

Before native creates any externally authoritative record, it may create at most one unpredictable private stage with `O_CREAT|O_EXCL`, keep that fd, write/fsync canonical bytes, capture full identity, and CAS-persist the corresponding `ARMED` journal value. The final record follows the same stage-before-publication rule.

A first CAS-publishes `ACK_PREPARED` with the complete immutable record set, full identities and an unpredictable cleanup quarantine basename per record before removing any record. Present records are movable/removable only when full identity and canonical bytes still match. After this durable intent, a missing subset is response-loss progress rather than proof from absence alone; retry fsyncs and rechecks the same recovery directory and continues only the remaining exact identities. For the ordinary `apply|review|undo` compatibility route, an immediate lost response to the final `ACTIVE(terminalCleanup) → IDLE` APPEND is reconstructible only from the still-adjacent physical PAIR: the older complete ACTIVE value must bind the requested operation/project and exact cleanup, the newer value must be IDLE, and fresh READ plus `assertTransition(older, newer)` must reproduce that same transition. Two explicitly accepted fail-closed availability residuals remain P2 candidates and do not weaken full-inode deletion safety. First, a helper hard-crash after the single random stage `O_EXCL` but before its identity reaches an `ARMED` slot leaves at most that one unreferenced private stage, performs zero public Markdown/History mutation, and locks all further native mutation for manual recovery; Main/native never adopts or deletes it. A second stage cannot be created while any such residue exists, preventing unbounded accumulation. Second, replacement of the journal basename with a stale/different valid clone can detach an in-flight held inode; post-write rebind detects it, preserves the foreign clone and locks manual recovery. Only a clone reproducing the complete current logical head and predecessor is equivalent. Automatic terminal convergence under either adversarial residual would require a protected external monotonic authority or relaxation of external-record full-inode authority and is not claimed.

Migration is one-way and fail closed. If the basename is absent and no legacy cleanup residue exists, startup uses `O_CREAT|O_EXCL` to initialize generation-zero `IDLE`, file-fsyncs it, directory-fsyncs it, and reopens the same root/recovery/journal authority. An invalid or partial initialization remains untouched and blocks the project. A legacy active `writcraft.changes-history-recovery/v1` JSON marker is never overwritten in place: compatibility recovery completes it under section 4.5, exact-clears it, and only then initializes the permanent `IDLE` journal from absence. An upgrade caught in Q/R/D without already persisted full publication identities is manual recovery; neither Main nor native may mint them from current same-byte records. Downgrade after permanent-journal initialization is unsupported and must fail closed rather than treating the binary/framed value as corrupt disposable state.

Before either manual recovery action writes any file, Main persists an internal `recoveryWritePending` durability latch and changes the public outcome to `manual_recovery`. Visible target bytes cannot clear this latch: a file or History rename may have succeeded while its directory `fsync` failed. Query/classify keeps the project locked. A retry must rewrite the selected exact file/History targets and successfully complete their durability proof before classification may release the latch.

Post-commit failures in pending-store settlement, residual publication, tree refresh, metrics, or onboarding transition cannot turn a proven commit into an ordinary failure. They return a committed warning or are recovered from the marker.

Onboarding confirmations and residual review capabilities are one-time in-memory authorities, not durable transaction facts.
