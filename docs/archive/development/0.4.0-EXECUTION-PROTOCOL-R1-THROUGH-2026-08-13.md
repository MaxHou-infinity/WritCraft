# WritCraft 0.4.0 封版恢复执行协议

> 编号：`WRC-0.4.0-EXEC-R1`
> 生效日期：2026-08-11
> 状态：**当前派工控制文件；不改变 `WRC-0.4.0-R1` 的产品范围、失败矩阵或发布边界**
> 当前锁定：**只推进 Stage A；Stage B 的独立纯层/App 下游纵切保持冻结，但必须在 Stage A 签收后补做真实 A→B 连续旅程；Stage C/D/E 不得开工**

本协议用于纠正 0.4.0 开发中已经发生的阶段跳跃、窄层绿灯冒充产品完成、测试未进入顶级门禁、长期脏工作树和同类 P1 反复。它只约束执行方式，不降低任何安全合同，也不新增产品功能。

## 1. 当前单一派工入口

当前只允许按以下顺序完成 Stage A；每个字母后缀都是独立 checkpoint，不得合并成数日横切：

1. **A0 可执行门禁**：先建立 0.4 测试清册、静态 orphan check 和 current-component 顶级 npm gate。现存测试必须显式归类为 component、GUI 或 completion evidence；Stage A component 绿灯固定 `completionEligible=false`。A0 未绿不得新增 A1 实现或测试。
2. **A1a finalize/ACK**：只收口 CREATE finalize/ACK cleanup。
3. **A1b mixed/rollback**：只收口 mixed EXISTING 与 `ROLLBACK_CREATE` 的同事务 authority。
4. **A1c Safe Undo**：只接通 permanent-journal Safe Undo 当前生产链。
5. **A2a create/list**：接通 Main handler、IPC、preload、Renderer，让 App 创建并列出真实 committed snapshot。
6. **A2b compare**：只接通 snapshot compare、diff 与 stale/conflict 显示。
7. **A2c restore/undo**：只接通选择性 restore、History reconcile 与 Safe Undo 用户链。
8. **A2d delete**：只接通 destructive confirmation、delete、committed reconciliation 与刷新。
9. **A3 Stage A 签收**：完成 Snapshot helper package、`npm test`、`npm run verify`、真实 Electron、Computer Use、独立复审和 exact Stage A checkpoint commit；它不是 0.4 candidate。
10. **A→B 重签**：Stage B 逻辑不重做；只用 App 创建的真实 snapshot 重跑“创建→选择→预检”连续旅程，禁止直接 seed committed snapshot 作为集成签收。

A1a–A2d 每项都必须各自具备 production 首红、定向退出证据、独立复审和 exact checkpoint；前一项未签收，不得把下一项代码并入同一 WIP。

以上十项未全部完成前，不得实现 DOCX、Graph 新视图或 Stage E 作者旅程。发现 Stage C/D/E 的必要前置缺口，只记录到本文件的阻断清单，不切换当前派工。

## 2. 每个 checkpoint 的唯一完成定义

一个 checkpoint 只有同时具备以下证据才可签收：

1. 冻结 exact authority/state/failure matrix，并在**真实生产边界**运行首个反例；
2. 最小生产纵切可运行，不依赖 direct storage seed、no-op helper、伪造 receipt 或绕过 Main 的测试后门；
3. 定向测试通过，所有新增/改名的 `verify-v0-*.js` 已在同一 change set 进入测试清册与当前 component/stage 顶级 npm script；
4. 受影响真实 Electron 通过；涉及 GUI、原生对话框、Pages 或系统权限时再完成 Computer Use；
5. 新的独立 reviewer 在实现稳定后复审，P0/P1 清零，P2 明确归类；
6. 源码、测试、合同、状态账本和 exact commit/diff 指向同一候选。

缺少任一项时，只能称为 `checkpoint`、`focused evidence` 或 `integration pending`，不得称为 Stage、App、候选或封版完成。

## 3. 防止假绿与重复返工

- **前一阶段真实产物原则**：下游阶段必须消费前一阶段通过生产入口创建的真实产物。fixture seed 只验证下游纯层，不能签收跨阶段旅程。
- **production adapter 原则**：涉及 filesystem、fd、receipt、journal、capability、IPC 或 package 的结论，必须在相应 production adapter 上产生故障证据；fake 结果不得自证真实边界。
- **先红后写**：先在最低成本且能跨越声称边界的测试上稳定复现首红，再写实现。没有首红的 delegated checkpoint 永久记录为证据纪律缺口，不能事后补写成“按计划通过”。
- **同类 P1 止损**：同一 authority 或 state transition 连续两轮独立复审仍出现同类 P1，立即停止补丁；回到完整状态机、持久 preimage 和跨进程三态重新设计。未经新矩阵复审不得继续写实现。
- **测试注册门禁**：任何新增或改名验证脚本必须在同一 change set 更新清册并进入当前 component/stage 顶级 npm script；静态 orphan check 未绿时禁止继续实现。`npm test` 绿色不得覆盖未注册脚本。
- **红灯分类后再重跑**：同一完整 suite 在红灯分类、定向复现和修复证据完成前不得反复重跑。环境红灯只允许原命令在批准环境复跑一次；结果成对保留。

## 4. WIP 与资源止损

- 同时只允许 **1 个主 checkpoint + 最多 1 个不修改同一 authority 的支持任务**。多个 agent 不得并行编辑同一状态机、schema 或事务链。
- 主 checkpoint 必须在一个工作回合或 90 分钟内给出可检查产物：首红、最小实现、测试结果或明确阻断。委派支持 lane 仍按 `AGENTS.md` 的 5–10 分钟窗口交付中间检查点；90 分钟不是允许代理静默运行的时间。只有日志增长、文档叙述或更多 schema 不算 checkpoint。
- 只有定向门禁全绿并准备进入独立复审、候选复核或环境分类时，才运行完整 `npm test`/`npm run verify`；不得在每个机械修改后重复全量回归。
- reviewer 开始时记录全部被审文件 hash；审查期间任何 hash 漂移都立即使该轮无效，停止修改并从新 hash 重启完整 finding batch。一次性收齐发现后再修改，修改完成后由同一 reviewer 定点复核。
- 每个独立签收的纵切必须形成 exact local checkpoint commit。若当前工作树客观上不能提交，必须暂停下一纵切，并生成 exact file manifest、每个文件 hash、完整 diff 绑定和 reviewer 签字；只有该可复现冻结边界或所有者明确批准的其他隔离方式可以代替 commit。写一句“不可提交原因”不能解锁后续工作。push、Tag、Release 和发布仍需所有者另行授权。
- 新增 helper/schema/事务分支前必须说明它关闭哪个当前 P0/P1；如果只是提高漂亮的测试数字、重复现有 authority 或处理未批准威胁模型，停止实现并记录候选项。

## 5. 顶级门禁与候选账本

Stage A 开工前必须由 A0 建立并维护 0.4 测试清册、静态 orphan check 与 `verify:0.4:current-components`。它只表示当前 component regression 已注册并通过，不是 Stage A 完成。A3 再建立真正的 Stage A 签收门禁；`verify:0.4:candidate` 只能在 Stage C/D/E 全部实现并进入封版候选时建立。门禁至少包含：

- 所有当前 0.4.0 新增测试的静态注册检查；
- Stage A Snapshot create/list/compare/restore/delete/Safe Undo/package；
- 已完成 Stage B delivery preflight 与 native image decode；
- `npm test`、`npm run verify`、受影响真实 Electron；
- Stage A 签收时加入 production App、helper package、真实 Electron 与 Computer Use；candidate 时再加入 DOCX/Graph/Pages/作者旅程。

状态账本顶部只保留一页以内的“当前控制块”：当前 checkpoint、退出条件、最新首红、仍开放 P0/P1/P2、exact commands 和下一动作。详细轮次、旧测试数字和已被取代的 checkpoint 移入归档证据，不再留在活动派工区。

## 6. 暂停与升级条件

出现以下任一情况时暂停当前执行并向所有者报告，不自行扩大目标：

- 需要改变 `WRC-0.4.0-R1` 产品范围、威胁模型或作者体验；
- 同类 P1 已触发两轮止损，仍没有经复审的新矩阵；
- 真实生产边界无法在当前环境运行，且没有等价的批准环境；
- 当前 checkpoint 需要修改 Stage C/D/E 才能成立；
- 预计需要新增第二套索引、扫描器、Graph、History 或 recovery authority；
- 无法把新增测试纳入顶级门禁，或无法形成 exact checkpoint。

安全 fail-closed、测试失败或实现困难本身不是目标变更理由；先在冻结范围内修复或报告阻断。
