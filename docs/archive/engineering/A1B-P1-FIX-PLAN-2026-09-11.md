## 3. P1-3 与 P1-4 是同一个变更（关键结论）

`docs/0.4.0-A1B-EXISTING-STATE-MATRIX.md` §6 与 journal schema 共同决定：

- ACTIVE → IDLE 的**唯一**合法路径要求 `terminalCleanup !== null` 且
  `nativePublication.state === 'ACK_COMMITTED'`
  （`changes-history-marker-journal-schema.js` 的 `assertJournalValue` / `assertTransition`；
  合同 `CHANGES-HISTORY-RECOVERY-V1-CONTRACT.md` 同）。
- ROLLED_BACK 之后 journal 实际为：`state:'ACTIVE'`、`nativePublication` =
  `CREATE_MISSING` / `state:'COMMITTED'`、`existingTerminalPublication:null`、
  `terminalCleanup:null`、marker `state:'applying'`。
- 因此只做 P1-4（服务返回零写入终态）会让项目**永久锁在 ACTIVE**，下一个恢复操作无法开始。

结论：**P1-3（分阶段 durable publication）与 P1-4（服务消费 + 收敛到 IDLE）必须同一
change set 闭合。**

## 5. 选项 B 的落地顺序（每步保持门禁绿）

### 5.0 阻塞前提（必须先解决）：native rollback wire 绑定了 journal 字节镜像

这不是纯 Main 侧改动。main 现行 native wire 把**活的 journal 字节镜像**写进 rollback 请求：

- `public-markdown-native-schema.js`：`buildRollbackCreateHeldBinding` 需要 `markerByteLength`
  + `markerIdentity` 并与 `existingAuthority.request.journalMarkerBinding.journalFileIdentity.contentSha256`
  交叉校验；`buildRollbackCreateRequest` 把 `markerByteLength` / `markerIdentityDigest` /
  `journalMarkerDigest` 写进请求；`rollbackCreateRequestDigest` 是请求的 digest；
  `rollbackCreateRecordNames` 由该 digest 派生 control/receipt basename。
- native C：`rollback_request_digest_valid` 重算同一 digest；`rollback_held_authority`
  在 `HELD_MARKER_FD` 上比对 size/sha/identity；`rollback_record_names` 由
  `request->request_digest` 派生名字。

后果：**每一次 WRCCHRJ2 APPEND 都改变 journal 字节 → authority 必须重建 → 重建改变
request digest → Q 的记录名改变 → D 再也找不到它们。** 因此「每阶段一次 CAS」在现行
wire 下**不可能**成立。

分支 `37e67e7` 的解法是把**活的 journal binding 从 request 移到 heldBinding**，并在
request 里改放稳定的 `existingJournalMarkerBinding`（分支 native schema + C 的
47/48/61 字段头 + `rollback_journal_valid`）。main 已经拥有可复用的
`existing_journal_marker_valid`（C `6206-6274`）与 `ExistingExecuteRequest`（`5849-5889`），
所以 C 侧是「重构 + 扩展 rollback 头字段」，不是新密码学。

**这是本批次唯一的硬前提，且它会改变已冻结的 native wire 头字段数，需要所有者确认。**

#### 5.0.1 为什么解耦成立（已一手验证，勿再"加固"）

必须区分**两个** journal binding，否则会误判解耦无效：

| 载体 | 来源 | 生命周期 |
|---|---|---|
| `request.existingJournalMarkerBinding` | `context.existingAuthority.request.journalMarkerBinding`（分支 `public-markdown-native-schema.js` ≈3948） | **存储值**。EXISTING authority 在 E 阶段被冻结进 rollback 的 `authorityBase64`，之后各阶段只从该 seed 重建，因此**不随 journal append 变化** |
| `heldBinding.journalMarkerBinding` | 每阶段 `captureExistingJournalAuthority` 重新捕获 | **活值**。重建 authority 时刷新，并由 authority header 交给 native 在 held fd 上校验 |

因此 request digest 在 Q/D/A 各阶段**保持不变** → `rollbackCreateRecordNames` 保持不变 → D 能找到 Q 写的记录。
分支的 `withFreshRollbackCreateAuthority` 在重建后断言
`rollbackCreateRequestDigest(rebuilt) === stored.requestDigest`，正是这条不变量的守卫。

`existingJournalMarkerBinding` 内部**仍然**含 `journalFileIdentity`（含整文件 `contentSha256`）与
frame/payload/marker digest —— 这是**有意**的：它绑定的是 E 时刻的存储快照，不是活文件。
不得为了"更彻底"而移除它们。

**main 侧前提同样成立**：`withExistingJournalBinding` 在 E 执行时构造活 binding，rollback 在
任何 journal append 之前就把它连同 `existingAuthority` 冻结进 `authorityBase64`（Q 本身不
append journal），所以首个 CAS 内的 `requestDigest` 从此稳定。

**因此本批次可以不引入 attempt latch**：attempt 的作用只是"在 Q 之前落盘 authority"，
而 Q 不改 journal，首个 CAS（`QUARANTINED`）已经承担了同样的冻结职责。这是相对分支的
**有意简化**，不是遗漏。

> **2026-09-11 更正（上述"可以省略 attempt latch"的推论是错的，已作废）**
>
> Q 虽然不改 journal，但它**会移动 receipt-owned MISSING leaves 到私有 quarantine**。
> 若没有 attempt latch，崩溃窗口为：
>
> - 崩溃在 Q 之前：journal 仍是 `CREATED_RECEIPT`，fresh R 复现 `UNCOMMITTED`，可重入 rollback ✅
> - **崩溃在 Q 之后、CAS 之前：创建叶已被移走，但 journal 没有任何记录**。重启时 fresh R
>   在公开路径上找不到 CREATE publication 声称存在的叶 → `UNKNOWN`/manual ❌
>
> 即：省略 latch 会把"**A 删除记录后才 CAS**"的不可恢复窗口，换成"**Q 移动记录后才 CAS**"
> 的同类窗口 —— 正是 P1-③ 要消灭的失败类别。
>
> **结论：attempt latch 是必需的，必须移植。** 其作用是让「Q 已开始」在 Q 破坏性动作之前
> 落盘。latch 之后、Q 完成之前崩溃时，重启只做 fresh R、**绝不重放 Q**；若 Q 从未真正执行，
> R 返回 `UNCOMMITTED` 并落到 `CHANGES_MANUAL_RECOVERY_REQUIRED` —— 这是分支有意的
> fail-closed 姿态，需在状态矩阵中写明，避免 reviewer 误读为缺口。

## 8. 实施期决策记录

### 8.1 Phase 2b（把 rollback publication 显式绑进 CLEANUP）——本轮不做，理由如下

分支设计把 rollback publication 的 digest 绑进 `CLEANUP` / `CLEANUP_BUILD` /
`PUBLICATION_SET`；本批次**未采用**，因为 D 的真相已经被密码学绑定，路径是：

- `terminalCleanup.terminalPhaseDigest` = `ROLLED_BACK` phase 对象的 digest，而该 phase
  携带 `rollbackReceiptDigest`（D 的 final record digest）；
- `terminalCleanup.publicRecordDigests` **直接包含** `settle.finalRecord.finalRecordDigest`
  以及每个 quarantine token 的 `controlDigest` / `receiptDigest`；
- journal value 的 `valueDigest` 链覆盖 `rollbackCreatePublication` 本身。

`publicationState` / `publicationDigest` 这一通道语义上留给 CREATE / EXISTING publication，
本路径正确取 `'NONE'`（schema 强制 `nativePublication === null` 与之一致）。
因此显式绑定属于**纵深加固**而非正确性缺口；若 reviewer 仍要求，可在不改语义前提上追加。

### 8.2 环境限制：`npm test` 最末的 packaging 检查在本机必然失败

`npm test` 完整跑完 `pretest` → `test`（63 套件）→ `posttest` 链条，**唯一**失败点是链条
最末的 `tests/verify-v0-npm-preview.js:51`：

```js

assert(Array.isArray(report) && report.length === 1);
```

本机实测 `npm --version` = **12.0.2**、`node --version` = **26.8.1**，而 `v0/package.json`
声明 `engines: { npm: ">=10 <12", node: ">=22.12.0" }` —— **本机不在声明范围内**。
npm 12 的 `npm pack --dry-run --json` 已改为输出以包名为键的**对象**（实测顶层类型
`object`，key 为 `writ-craft`）而非数组，该断言因此必然失败。

- 与本批次改动**无关**：断言只检查 npm 自身的 JSON 输出形状；改动未触及 `package.json`

- CI（`.github/workflows/verify.yml`）用 `actions/setup-node` + `node-version: 22`，自带

## 9. 【重要】边界测试发现：P1-3 的 D 阶段仍未闭合（2026-09-11）

为满足 reviewer「Q/D/A 每个 publication/CAS/response-loss 边界」的要求，本批次新增了
边界的崩溃/响应丢失测试。结果是 **Q 与 A 已闭合，D 未闭合**：

### 9.1 缺陷：native D 已提交但响应丢失后不可恢复

最小复现（`v0/tests/verify-v0-snapshot-restore-mixed-journey.js`，
`KNOWN DEFECT (P1): lost native D response leaves the rollback unrecoverable`）：

1. 在 D 的 spawn 边界丢弃**第一次** D 的响应（helper 实际已执行并提交 D，只是响应丢失）；
2. 此时 journal = `ACTIVE`，`rollbackCreatePublication.state === 'QUARANTINED'`，
   marker phase = `CREATE_ROLLBACK_QUARANTINED`；D 的真相**已经durable**；
3. 重启走 `rollbackUncommittedExistingRestore` → `settleRollbackCreate` 重发 D；
4. native D 返回 **UNKNOWN** 而非 `FINALIZED`，JS 抛
   `CHANGES_MANUAL_RECOVERY_REQUIRED('rollback-create delete truth is unknown')`；
5. journal 永远停在 `QUARANTINED` → **自动路径不可恢复**。

第二个表征测试 `KNOWN DEFECT (P1): rollback restart after D ran before the ROLLED_BACK
CAS cannot settle deleted truth` 是同一边界的另一入口。

### 9.2 影响判定

- 这不是"测试脚手架问题"：D 已经在**生产 native 边界内**提交了真相，问题是**重发 D 不幂等**
  —— quarantine 已被删除、final record 已封存时，重跑 D 无法回到 `FINALIZED`。
- 因此 **P1-3 不能声称已闭合**。reviewer 要求的 "Q/D/A 每个 publication/CAS/response-loss
  边界" 中，D 的 response-loss 边界仍然失败。
- 两个测试当前是**表征测试（characterization test）**：它们把缺陷钉住并命名，使
  `KNOWN DEFECT (P1)` 显式可见。它们绿灯**不代表** P1=0；相反，它们的存在正是缺陷的durable
  证据。
- 严禁把 `18/18` 解读为 A1b 可签收。**A1b 仍为 NO-GO，至少有一个 P1 子边界未闭合。**

### 9.3 建议修复方向（未实施）

让 D 在"quarantine 已删除 + final record 精确存在"时返回 `FINALIZED`，即把 D 变成
真正幂等：重跑时优先校验已封存的 final record（含其 identity 与 digest），而不是先去
重新删除 quarantine。这属于 **native C 改动**，必须按当前 WRCCHRJ2 + held-binding wire
适配，并补 `D 重放/响应丢失` 的正反例。
