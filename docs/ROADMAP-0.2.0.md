# 笔触 WritCraft 0.2.0 开发路线图

> 路线图编号：`WRC-0.2.0-R1`  
> 批准日期：2026-08-03  
> 对应产品版本：`writ-craft@0.2.0`  
> 版本主题：日常写作工作区  
> 当前状态：**候选验收完成；已获所有者授权执行发布**

本文件是 `docs/ROADMAP.md` 为 0.2.0 指定的详细版本合同。阶段 0 → A → F 已完成并通过验收；产品版本号、npm、Tag/GitHub Release 和 App/ZIP 发布现已获得所有者明确授权，发布证据以 `v0/DEVELOPMENT-STATUS.md` 的最终记录为准。

## 1. 一句话目标

让作者每天打开一个长篇写作项目后，不需要自己翻遍文件树、Graph、Sources 和 Changes，就能立即知道：**项目现在是什么状态、上次写到哪里、有哪些事情需要处理，以及怎样一步回到对应正文。**

0.1.2 解决的是“AI 能否安全地帮助作者修改”；0.2.0 解决的是“作者能否轻松掌握并继续自己的写作项目”。

## 2. 为什么要做这个版本

当前产品已经具备项目、文件、段落三级写作能力，但项目越大，作者越容易遇到四个问题：

1. 打开项目后只能看到文件树，不知道整体进展和待处理事项。
2. 长章节需要反复滚动，难以快速找到某个标题或段落。
3. 文件、标题、人物、问题和待审修改分散在不同入口，查找成本高。
4. 重新打开项目或从审阅返回正文时，容易丢失上次的阅读和编辑位置。

因此，本版本不增加另一套 AI，而是把已有的本地项目事实整理成一个可操作的工作区。

## 3. 冻结的产品原则

1. **本地事实优先**：驾驶舱、大纲和快速打开只使用 Main 已验证的项目文件、History、Changes、Graph 与来源状态，不调用模型生成“项目进度”或“下一步建议”。
2. **所有信息都能行动**：每张卡片、每条搜索结果都必须能跳到真实文件、标题、问题、证据或审阅对象，禁止只展示数字。
3. **不猜作者是否写完**：系统可以显示字数、是否为空、是否只有骨架、是否存在待审修改或问题，但不能仅凭篇幅推断“章节已完成”。
4. **不复制权威状态**：新界面只聚合现有 Main 权威数据，不在 Renderer 建立第二份项目真相。
5. **零新增写入权限**：驾驶舱、大纲和快速打开只负责查看与导航；正文写入仍经过编辑器、Changes/Diff 与作者确认。
6. **安静且快速**：打开工作区不产生付费调用、不上传正文、不阻塞编辑器；索引失败时仍可继续写作。

## 4. 0.2.0 必须交付的能力

### 4.1 项目首页（项目驾驶舱）

项目首页集中显示：

- 上次编辑的文件和位置，可一键“继续写作”；
- 项目 Markdown 文件数、正文总字数和最近编辑文件；文件数与字数属于同一摘要区，点击后展开按文件统计，不作为无目标的独立卡片；
- 待审 Changes，可直接进入对应 Diff；
- Graph 中尚未解决的问题，可直接定位问题及原文依据；
- 已有确定性诊断能够识别的来源缺口；
- 各章节的可验证状态，例如“空白”“仅有骨架”“已有正文”“存在待审修改”“需要处理问题”。

章节状态可以叠加显示，但不得自动出现“已完成”。如未来需要“已完成”，应由作者主动标记，并另行冻结产品合同。

当前待审 ChangeSet 是进程内能力，因此项目首页只显示**当前会话仍然有效**的待审对象。0.2.0 不得用私有缓存伪装重启持久化；若未来要求跨重启恢复待审 Diff，必须另立写入和恢复事务合同。

### 4.2 当前章节大纲

- 根据 Markdown 标题生成层级大纲，并随当前文件更新。
- 点击标题跳到准确位置；滚动正文时同步突出当前章节。
- 支持重复标题、长标题、中文标题和深层标题，定位不能只依赖标题文本。
- 支持键盘操作、折叠层级和窄窗口。
- 本版本不支持拖动大纲重排正文，避免把导航功能扩大成写入事务。

### 4.3 快速打开

提供统一的本地查找入口，建议使用 `⌘P`：

- 文件；
- Markdown 标题；
- Graph 已索引的人物、实体和问题；
- 待审 Changes。

结果按类型分组，显示所属文件和必要的路径信息，支持键盘选择并直接定位。0.2.0 不做 AI 语义搜索、不搜索互联网，也不借此新增跨项目记忆。

`⌘P` 是快速导航，现有 `⌘⇧F` 继续负责全文内容搜索。两者必须共用 Main 权威文件/标题索引，禁止各自扫描项目形成第二套真相。

### 4.4 可恢复导航

- 恢复上次打开的标签、当前文件、光标、选区和滚动位置。
- 从驾驶舱、Graph、来源或 Changes 跳入正文后，能够返回原来的工作区位置。
- 项目切换后不得恢复另一个项目的状态。
- 文件被移动、删除或外部修改时，安全降级到仍然存在的最近位置，不伪造旧定位。

现有 workspace 已能保存标签、当前文件、光标和滚动位置；0.2.0 是在既有能力上补选区、返回路径和安全 schema 迁移，不得按“从零重写恢复系统”估算或实现。

### 4.5 连续的日常写作闭环

作者应能完成以下旅程而不迷路：

> 打开项目 → 查看状态 → 定位一项工作 → 编辑或审阅 → 返回项目状态 → 继续下一项工作

项目首页是编辑器的主工作区页面，不塞进右侧 AI 面板。建议在左侧常驻功能栏提供“项目首页”图标；打开已有项目时默认恢复上次写作位置，而不是每次强制覆盖为首页。

## 5. 分阶段实施路线

### 阶段 0：权威基线与历史资产清理

**完成状态（2026-08-03）**：已通过。Main → Renderer 反向依赖归零，跨进程纯逻辑迁入 `src/shared/`；旧 Project Plan 运行时与历史测试物理移除；Navigation 每张建议只保留一个 `changes` capability；依据链接、统一正文 Diff、`needs_sources` 与独立 Research 均保留。最大 goal、4096 evidence enum、最大 Unicode 输出和精确 1 MiB request 的组合 fixture 通过，`+1 byte` 在 provider 前拒绝。`npm test`、完整 `npm run verify`、真实 Electron 37/37 与独立复审 P0/P1=0。阶段 A 之前不得重开本阶段已关闭事项。

在开发新界面前先消除会误导实现的旧产品分支：

- 完成文档索引、状态账本瘦身和失效资料归档；
- 修复现存 Main → Renderer 反向依赖：把 `block-anchor`、`context-selection` 等跨进程纯逻辑迁入 `v0/src/shared/`，Main 与 Renderer 共用同一实现；增加静态门禁和行为等价测试，确保 Main 不再 `require` Renderer，并同步 npm 包文件清单；
- 0.2.0 新 IPC 使用独立 service/handler 接入，不继续把产品逻辑堆入 `main.js`；只做渐进拆分，不在本版本重写 Main；
- 删除已退役且仍被 npm 宽泛 allowlist 打包的 Project Plan Main/Renderer/Changes 死代码、历史 fixture 路由与不可达 Electron 阶段；
- 保留 Chapter 内部区块规划和普通 Changes 范围预检，不能按名称包含 `plan` 误删合法能力；
- 把 Writing Navigation 的公开动作合同、生产模型和 Renderer 统一为 `changes-only`，删除不可达的旧默认 `open/research` 动作分支；保留 `submit_localized_edits`、Main-owned evidence locator、统一“建议 → 正文内 Diff”旅程，以及从 Sources 主动进入的独立高级 Research；
- 为上述 Navigation 清理增加最短回归：“生成建议 → 处理建议 → 正文内 Diff”，并证明依据链接仍能定位、独立 Research 仍能单独启动；
- 补最大合法 Navigation 请求的 Unicode、evidence marker、动态 enum 与精确字节 fixture，不改变模型协议、token 或付费重试策略；
- 冻结 `⌘⇧F` 全文搜索、workspace/v1 恢复、进程内 pending Changes 等既有能力的复用/迁移矩阵；
- 在删除历史模块后重跑当前公开面、npm 包文件清单、完整回归和真实 Electron 基线。

**退出条件**：Main 不再反向依赖 Renderer；发布包和现行运行路径不再包含旧 Project Plan 用户能力；Navigation 合同与生产 `changes-only` 一致且最短统一旅程、依据定位、独立 Research 均未回归；历史测试只存在于归档证据而不参与当前 sign-off；完整基线通过，独立复审 P0/P1 为 0。阶段 0 不新增 0.2.0 用户界面。

明确每项数据的来源、刷新时机、空状态、失败状态和跳转目标；冻结章节状态定义、定位标识、统计摘要的钻取目标和 300 文件性能样本。同时冻结性能验证环境、冷/热启动、缓存状态、计时起止点，以及索引超时后的明确降级界面。

**退出条件**：合同、失败矩阵、UI 信息架构和测试计划完成独立复审，P0/P1 为 0；本地聚合超过 5 秒必须结束加载态并进入可继续编辑、可手动重试的降级终态。此阶段不制作假数据 UI。

## 6. 可衡量的验收标准

1. 打开已有项目后自动恢复上次写作位置，作者无需额外点击即可继续写作；作者主动进入项目首页后，从任一可操作卡片最多一次点击到达对应待处理对象。
2. 项目首页中的每项状态都能追溯到 Main 权威数据；断开网络不影响使用。
3. 当前章节大纲点击后准确定位；重复标题不会跳错位置。
4. `⌘P` 可完全通过键盘查找并打开文件、标题、实体、问题或待审修改。
5. 外部新增、修改、移动或删除 Markdown 文件后，字数、大纲和相关卡片正确更新；无法确认新鲜度时明确降级，不展示陈旧真相。
6. 典型项目（不超过 50 个 Markdown 文件）应在 1.5 秒内出现可操作的首屏；300 文件验收项目应在 3 秒内出现可操作首屏，较慢内容可以渐进补齐。阶段 A 必须冻结测试机器、项目样本、冷/热启动与缓存条件，并以“项目打开请求发出”到“首页或已恢复编辑区可接受输入”为统一计时边界。
7. 任何索引、恢复或导航失败都不得修改正文或阻止作者继续编辑；本地聚合超过 5 秒必须停止加载并显示“项目统计暂不可用”，保留编辑、重试和打开文件树三个恢复动作。
8. 在窄窗口、200% 缩放、长章节和键盘操作下，核心旅程仍可完成。
9. 真实作者能独立完成“查看状态 → 定位 → 编辑/审阅 → 返回”的旅程，并能用自己的话说明当前所在位置。
10. 候选版本独立复审达到 P0=0、P1=0；P2 有明确影响、规避方式和发版决定。
11. 每条验收证据必须注明执行者、exact commit、测试项目或隔离副本、运行方式和结果；能由 Nana 可靠执行的旅程不得转交所有者重复操作。

性能数字在阶段 A 中以固定测试机和样本复核后冻结；若证据证明不现实，应在编码前提请所有者修改，不得开发到最后再降低标准。

## 7. 明确不做

- 不修改 0.1.2 已签收的 AI 生成协议、统一写作任务流或 Diff 权限边界。
- 不新增 AI 任务中心、多模型选择、云同步、账户、收费或多人协作。
- 不让 AI 评判章节是否完成，也不生成软件项目式任务计划。
- 不做 AI 语义搜索、外部网页 Research 或跨项目搜索。
- 不重做 Graph，不将驾驶舱扩成独立知识库产品。

## 8. 自动化优先的验收责任

0.2.0 默认采用“机器验证机制、Nana 操作界面、所有者只做必要判断”的分工：

1. **Nana 自主完成**：专项测试、完整回归、真实 Electron、Computer Use 界面操作、键盘和窄窗口检查、外部文件变化、失败/超时/恢复、性能采样和证据整理。执行顺序固定为“确定性专项/服务测试 → 真实 Electron harness → Computer Use 视觉与系统交互补充”；Computer Use 不代替可稳定重复的回归脚本，并记录 exact commit、App 构建、项目副本和 profile。
2. **所有者最小参与**：只完成一次最短的 0.2.0 端到端旅程并确认审美、信息理解与是否真正有帮助；授权真实稿件、隐私、付费调用、发布等外部权限；完成自动化客观上无法可靠代替的动作。
3. **禁止把人工当测试脚本**：不得因自动化缺口而反复要求所有者执行接受、拒绝、撤销、重启等机械动作；应先补 harness 或使用 Computer Use。
4. **自动化不能冒充主观签字**：脚本绿色只能证明功能与状态边界，不能代替作者对信息是否清楚、工作流是否自然的最终判断。
5. **减少重复验收**：生产源码未影响已经签字的旅程时，不重跑该旅程；源码发生影响时，只重验受影响路径，并明确说明为什么需要所有者再次参与。
6. **保护真实稿隐私**：真实长文界面截图、录屏和正文片段默认不得进入 Git、测试日志或 Nowledge Mem。证据只记录内容无关字段；只有 fixture，或经所有者明确授权且完成脱敏的素材，才可作为视觉证据留存。

## 9. 代码健壮性与可维护性门禁

1. **模块边界清楚**：Main 负责文件、索引、定位和项目状态权威；Renderer 只展示并发送受限意图。Main 禁止引用 Renderer；两端都需要的无副作用逻辑进入 `src/shared/`。不得为赶进度在 UI 中复制业务真相，也不得继续无边界扩张单个巨型文件。
2. **失败必须可收口**：所有异步操作处理超时、取消、迟到结果、项目切换、文件漂移、重复提交和部分失败；清理动作绑定同一 operation owner，不留下永久 busy、陈旧索引或跨项目状态。
3. **关键代码必须解释“为什么”**：对权限边界、状态机、并发保护、revision/locator、降级策略和非显然算法添加清晰注释；注释说明约束、失败方式和修改时必须维持的不变量，不复述代码表面语法。
4. **公开内部合同**：0.2.0 新增或实质修改的 Main service、IPC/preload 方法和复杂状态对象必须有简洁的 JSDoc 或邻近合同，写明输入、输出、稳定错误、权限所有者和副作用；新增模块使用可搜索的 kebab-case 名称。未被本版本触及的旧模块不开展全库补注释。
5. **代码与说明同步**：若模块结构、数据流或运维方式改变，同一提交更新对应合同、`v0/DEVELOPMENT-STATUS.md` 及必要的架构/故障排查说明，禁止只在聊天记录里解释。
6. **健壮性必须有反例测试**：除成功路径外，至少覆盖空项目、损坏缓存、外部修改、项目切换、超时、取消、重复标题、过期定位和 300 文件压力样本。
7. **独立可维护性复审**：每阶段退出前，由非实现上下文检查命名、职责、注释、错误处理、重复逻辑和文档可追踪性；P0/P1 未清零不得进入下一阶段。

代码注释以帮助未来维护者安全修改为标准，而不是以注释数量为标准。简单赋值和显然分支无需注释；权限、并发、事务与兼容性陷阱不得依赖口头记忆。
