## 一、产品定义

### 1.1 一句话定义

**笔触 · WritCraft 是中国第一款 Cursor 范式 AI 写作 IDE——把结构化大纲 / 逐句悬浮 Diff / Plan Mode / 研究内联 / 多模态生成 / 结论溯源，全部塞进一个界面，让专业长文作者在自己的地盘上把 AI 当副驾驶，而不是被工具切换打断心流。**

### 1.2 目标用户：4 类作者画像 + 痛点

| 用户类型 | 代表人物 | 核心痛点 |
|---------|---------|---------|
| **方法论书籍作者** | Ray Dalio / Cialdini / 管理学作家 | 50–80 万字结构化管理；原则树 + 案例对照；出版前需要 6–12 周分层冷却修订 |
| **学术综述作者** | 医学/法律/经管综述写手 | PRISMA 流程严格；300+ 篇文献管理；同行评审格式要求 |
| **长篇小说作者** | Stephen King / 纳博科夫派 | 10 万字以上非线性管理；伏笔追踪；卡片法 vs 大纲法两派并存 |
| **咨询报告作者** | 乙方顾问/战略分析师 | 模板化输出；图表自动生成；客户风格对齐 |

**通用痛点**（4 类作者共同持有）：

- 写 1 小时，切换 4–5 个工具（写作/对话 AI/浏览器研究/图片生成/笔记）
- Notion 写几千字以后文档开始卡；Scrivener 零 AI；ChatGPT 写完一段上下文就断
- AI 给的建议像黑盒——不知道改了什么、为什么这么改、结论从哪来
- 长文修改无从下手——不知道初稿差在哪里，AI 改完不敢用

## 二、V0 范围

### 2.1 明确做什么

1. **Plan Mode 5 模板**（开场 / 主旨 / 大纲 / 立意 / 收尾）—— 可选辅助，不是强制入口
2. **⌘K 逐句悬浮 Diff 修改**—— 选中文字 → M2.7-highspeed <200ms 返回修改建议 → 原文删除线 + 高亮 → Tab 接受 / Esc 拒绝
3. **章节大纲树**—— 左侧层级折叠，支持拖拽排序
4. **⌘L 全局对话**—— @chapter 引用替代 @file；M3 1M tokens 覆盖整本书上下文
5. **⌘R 深度研究 + 自动脚注**—— 5 类来源模板；结论 / 来源 / 边界三段式标注
6. **图像生成**—— image-01 章节插图，$0.0035/张，手动触发
7. **结论溯源**—— 每条 AI 输出标注来源 + 边界，不裸输出
8. **MiniMax M2.7-highspeed + M3 双引擎**—— M2.7 做 ⌘K 实时修改；M3 做长文生成 / 全局对话

### 2.2 明确不做什么（4 条红线）

> V0 功能边界由以下 4 条否定清单严格框定，任何"感觉应该做"的功能都要先过这 4 条：

| # | 不做的事 | 原因 |
|---|---------|------|
| **不做价值判断** | AI 不替用户决定"观点 X 比观点 Y 更好" | 专业作者的判断力是核心资产，不能外包给 AI |
| **不对接出版商 V2** | V0 不接任何出版社内容工作流 | T9 路线图 V2 才做，现在做会拖垮 V0 工期 |
| **不自动生成整本书** | 不做"一键生成全书"功能 | 质量不达标；违反专业作者群体对"自己写"的认同 |
| **不模仿作家风格** | 不训练/不输出"像 XXX 一样的文风" | 版权 + 伦理双重风险 |

**另外明确不做**：多人实时协作、移动端、语音转写、TTS、视频生成——这些 V1 以后再说。

## 三、核心场景 5 个

### 场景 1：方法论书籍作者写新章节

1. 打开 WritCraft，按 ⌘N 新建章节
2. 系统弹出 Plan Mode 5 模板选择——**可以跳过**（Murakami / King 派直接写也行）
3. 若选"大纲"：M3 生成 Part → Chapter → Section → Paragraph 多级树，每节点填 1–2 句本章主旨
4. 用户开始写正文，M2.7 在句尾显示 ghost text 补全候选
5. ⌘K 选中段落 → M2.7 给出 3 个修改版本 → diff 展示 → 用户 Tab 接受 / Esc 拒绝
6. ⌘R 输入研究问题 → 系统查 MiniMax Doc API 解析 PDF → 自动生成脚注（APA7 / MLA9 / Chicago17）

### 场景 2：学术综述写作者引用管理

1. ⌘R 选中引文 → 自动查学术数据库 → 生成 3 种引用格式
2. ⌘K 选中引用段 → "改写为更学术语气" → M2.7 给出 3 个版本 + diff
3. 用户接受 → 系统批注"引用源已验证 + 时间戳"

### 场景 3：长篇小说作者管理非线性结构

1. 纳博科夫式：建立 50–100 张场景卡片，每张卡片独立写作
2. 左侧大纲树支持拖拽重排——侦探小说凶手顺序可以最后排
3. 每张卡片独立调用 ⌘K，M2.7 补全当前场景下一句
4. 全局 ⌘L 问"这个伏笔还有几处没回收"——M3 扫描全项目给出列表

### 场景 4：咨询报告作者生成图表

1. 用户写"市场规模 100 亿，年增速 18%"
2. ⌘I 选中数字 → "生成柱状图" → image-01 生成 SVG 风格图
3. 系统自动插入 inline image + 标注数据来源

### 场景 5：律师写辩护状

1. Plan Mode 选"大纲" → 输入案件核心争议点
2. M3 生成 5 段式辩护大纲（受虐 / 防卫 / 减轻 / 程序 / 结论）
3. ⌘R 调判例数据库 → 自动脚注
4. ⌘K 改写"语言更克制更精确" → 律所风格对齐

## 四、写作数据模型

```
项目（Project）
  └── 章（Chapter）
        └── 段（Section）
              └── 句（Sentence）
                    └── 引（Citation）
                          └── 源（Source）
```

**核心实体定义**：

| 实体 | 定义 | 示例 |
|------|------|------|
| 项目 | 一本书 / 一篇论文 / 长篇项目 | 《原则》/ 糖尿病综述 |
| 章 | 书籍的章；论文的大节 | 第一章"痛苦即反馈" |
| 段 | 章节内的主题段；可折叠 | "1.1 时代背景" |
| 句 | 段落内的句子；AI 修改最小单位 | "福贵牵着老牛在田间走着。" |
| 引 | 对外部来源的引用；可追溯 | `(King, 2000, p.42)` |
| 源 | 参考文献条目 | King, S. (2000). *On Writing*. |

**来源追踪 JSON 格式**：

```json
{
  "sentence_id": "s_001",
  "content": "写作是纪律性痛苦的活动。",
  "attribution": {
    "source_id": "src_001",
    "page": "p.42",
    "quote": "Writing is back-breaking work.",
    "confidence": "high",
    "boundary": "仅适用于创意写作，学术写作可能有不同结论"
  },
  "ai_modified": true,
  "modified_at": "2026-07-14T10:00:00Z",
  "user_accepted": true
}
```

**AI 输出标准格式**：

```json
{
  "conclusion": "写作应该先计划后执行",
  "source": "T2: 4/4 文体均强调计划先于写作",
  "boundary": "适用于结构化长文；短推文/即时写作不适用",
  "evidence_level": "A"
}
```

## 五、Plan Mode 5 模板

| 模板 | 输入 | 输出 |
|------|------|------|
| **开场** | 写作目标 + 目标读者 | 开场钩子 3 个选项 + 理由 |
| **主旨** | 章节标题 | 本章核心主张（1–2 句）+ 支撑逻辑（3 点） |
| **大纲** | 主旨句 | Part → Chapter → Section → Paragraph 多级树；每节点填本章主旨 |
| **立意** | 段落 / 章节草稿 | 立意评估（强 / 中 / 弱）+ 具体强化建议 |
| **收尾** | 章节 / 全文章节 | 收尾呼应方式（3 种）+ 最终金句建议 |

**重要约束**：Plan Mode 是可选锚点，不是强制入口。T8 质询 N2 明确指出 King / Murakami 等顶级无大纲派作家可能强烈抵触 AI 介入写作规划，V0 必须允许用户直接开始写作，不弹模板。

## 六、⌘K 改写反馈机制

> **2026-07-15 决策反转**：本节原"删除线 + 黄色高亮"方案**改为"页面内红绿底色 Diff"**——见 §六 B 更新。
>
> 原因：主人在 V0 开发 Day 4 测试后，明确表态要在**编辑器页面（不是 ⌘K 侧栏面板）**直接看到 AI 修改/删除/新增的红绿底色。原以为"删除线 + 黄色高亮"信息密度更高，最终发现"红绿底色"对中文阅读流更直接、更醒目。

### §六 A、原方案（已废弃参考用）

**三层反馈 + 用户全控**：
```
第一层：悬浮 Diff 展示
  → 选中文字 → ⌘K → M2.7-highspeed <200ms 返回
  → 原文：删除线
  → 修改：黄色高亮
  → 不替代原文，用户确认后才应用

第二层：结论溯源标注
  → 每条修改右下角标"结论 / 来源 / 边界"
  → 鼠标悬停显示溯源卡片：
    - 结论：AI 生成内容的核心主张（1 句话）
    - 来源：标注文献编号
    - 边界：这个结论在什么条件下成立/不适用

第三层：接受 / 拒绝
  → Tab：接受当前修改
  → Esc：拒绝，等下一条建议
  → Ctrl+Enter：重新生成（保留相同上下文）
  → ⌘K+↑↓：切换 3 个候选方案
```

**撤销栈**：⌘Z 无限层撤销；所有接受 / 拒绝操作可回退。

**不做**：❌ 自动接受（失去控制）| ❌ 红绿差分（干扰中文阅读流，改用删除线+高亮）← **已被 §六 B 推翻**

### §六 B、当前方案（2026-07-15 起生效，V0 实施中）

**核心 UX 原则**：
- AI 修改**显示在编辑器页面内**（不是浮窗 / 侧栏 / 面板）
- 用户视觉焦点**永远在编辑区**——不要切走，不要弹窗

**Diff 视觉规范**：
```
┌─────────────────────────────────────────────────────────┐
│ 原文（删除的字）：红色底 `#f4d4d4` + 删除线              │
│ AI 新增的字：   绿色底 `#d8f0d0` + 无删除线              │
│ 未变的字：      默认（无底色）                            │
└─────────────────────────────────────────────────────────┘
```

**操作流程**：

```
步骤 1：选中段落
  → 用户在编辑区选中要改写的文字
  → 选中部分底色变蓝（浏览器默认）

步骤 2：⌘K
  → 编辑器内选中段旁边出现 inline Diff（红删 / 绿增 / 默认未变）
  → 接受 / 拒绝 / 重载 3 按钮以悬浮条出现（紧贴 Diff 上方）
  → 用户视线**永远在编辑区**，不需要看右侧 / 浮动面板

步骤 3：决策
  → ✓ 接受：删除红删字 + 保留绿增字，Diff 高亮消失
  → ✕ 拒绝：还原原文，Diff 高亮消失
  → 🔄 重载：保留选项，再调一次 M3 拿到新版本（替换当前 Diff）

接受 / 重载 / 拒绝快捷键（覆盖默认键位）：
  → Tab         = 接受
  → Esc         = 拒绝
  → Ctrl+Enter  = 重载
  → ⌘K         = 重新唤起（如果 Diff 已被拒绝）
```

**撤销栈**：⌘Z 接受 / 拒绝操作**全部可回退**（F2）。每次 Diff 接受成"原文 → Diff → 新文本"3 步栈。

**心流规范约束**（继承 §八 B）：
- 单一主题色（赭黄 `#d4a574`）= 标题、按钮、UI 强调
- Diff 红色 / 绿色 = AI 修改专用，不与其他 UI 元素冲突
- 内联 Diff 比 floating panel 更优（符合 §8 B.4："绝不弹窗"）

**关键验收**（V0 Day 5）：
- ✅ 用户选中一段 → ⌘K → **编辑区内**出现红删/绿增 Diff
- ✅ 接受按钮 → Diff 消失，文字变新版本
- ✅ 拒绝按钮 → Diff 消失，文字回原版本
- ✅ 重载按钮 → 重新调 M3，Diff 替换
- ✅ 用户视线**从未离开编辑区**

## 七 B、 MiniMax 鉴权与接入方式

> 主人原话：除了 APIKEY，也提供 auth 这种形式？是否可行？
> 当前决策：V0 只实现用户自带 API Key。OAuth、临时 Token 与企业 SSO 属于未来架构选项，必须在 MiniMax 官方支持、后端代理和密钥托管方案确认后再排期，不能把概念方案写成已支持能力。

### 7 B.1 4 种鉴权方式对比

| 方式 | 形式 | 适用场景 | 安全性 | 实现复杂度 |
|------|------|---------|--------|----------|
| **① API Key** | `sk-api-*` 或 `sk-cp-*` 静态 Token | 个人 / 小团队 | ⭐⭐ 中 | 低（1 个环境变量） |
| **② OAuth 2.0 Bearer** | 待官方与服务端方案确认 | 企业 / 多用户 | ⭐⭐⭐⭐ 高 | 中（未排期）|
| **③ 临时 Token（短时签名）** | 自建服务端代理签发 | 公共部署 / 多人共用一台 | ⭐⭐⭐⭐ 高 | 高（未排期） |
| **④ 企业 SSO（OIDC）** | 自建身份层对接 IdP | 大型企业 | ⭐⭐⭐⭐⭐ 最高 | 最高（未排期）|

### 7 B.2 鉴权方式选择流程图

```
用户启动 WritCraft
   ↓
检测应用 userData Key 设置 / 环境变量
   ↓
有 API Key？ ──── Yes ──→ 模式 1（直接用）
   ↓ No
引导用户在应用设置中输入 API Key

未来企业版才评估 OAuth / 服务端代理 / OIDC；V0 不显示未实现入口。
```

### 7 B.3 实际格式要求（Nowledge Mem 沉淀的真实踩坑）

> 警示：不同套餐、Key 类型和端点的能力可能变化。V0 已验证文本请求使用 MiniMax Anthropic 协议；图像能力必须按官方 `image_generation` 文档单独验证。不要根据 Key 前缀推断其必然支持某个模型。

| Key 格式 | 支持模型 | V0 推荐 |
|---------|---------|--------|
| `sk-api-*` | 以账户与官方端点实际权限为准 | ✅ 支持配置，调用前校验 |
| `sk-cp-*` | 以 Coding Plan 与官方端点实际权限为准 | ⚠️ 支持配置，调用前校验 |

### 7 B.4 安全设计

- ❌ 永远不在前端明文存储 API Key
- ❌ 不在 localStorage 存明文 Token
- 🟡 当前桌面 V0 保存到 Electron `userData` 下的 0600 配置文件；后续应升级为 Mac Keychain / Windows Credential Manager
- ⬜ Token 自动轮换尚未实现
- ✅ 调用只从 Main 进程发起，renderer 不持久化也不回显 Key
- ⬜ 服务端代理与脱敏调用审计属于企业版/公开服务阶段，V0 尚未实现

### 7 B.5 V0 优先级

| 阶段 | 支持的鉴权方式 |
|------|--------------|
| V0 | ① 应用设置中的 API Key（Electron `userData`）+ 环境变量开发回退；项目目录禁止 `.env` |
| V1 候选 | OS Keychain / Credential Manager；是否加入 OAuth 需官方能力和服务端方案评审 |
| 企业版候选 | 临时 Token 代理 + 企业 SSO（OIDC），均未承诺 |

## 八、F1–F10 合规硬规则

| # | 规则 | 适用场景 |
|---|------|---------|
| F1 | **AI 修改默认"建议"，绝不自动应用**——所有 diff 都要用户明确接受 | ⌘K / Composer / Plan Mode |
| F2 | **接受 / 拒绝 / 撤销全部可操作**——撤销栈无限层 | ⌘K / ⌘L / Composer |
| F3 | **每条 AI 输出标"结论 / 来源 / 边界"**——沿用 Max-AI 结论溯源规范 | 所有 AI 输出 |
| F4 | **不替代写作者做价值判断**——AI 不写"你认为 X" / "我主张 Y" | Plan Mode / ⌘L |
| F5 | **不替用户做归属判断**——不写"X 公司的 Y 报告"除非用户明确指定 | 模板 / 建议 |
| F6 | **prompt 禁止一个模板批量发送给所有用户**——必须按用户上下文定制 | 草稿 / 总结 |
| F7 | **候选人 / 引用合并可解释**——多字段匹配 + 用户主动确认 | 引用管理 |
| F8 | **字段级来源标注 + 时间戳**——删除日志不可删除 | 数据模型 |
| F9 | **所有 AI 操作写审计日志**——类型 / 时间 / 触发者 / 输入 / 输出 / 结果 | 全局 |
| F10 | **原始文件 90 天过期**——可配置延长 | 文档存储 |

## 八 B、 心流体验规范（视觉 + 交互）

> 主人原话：需要增加视觉和交互的体验说明，确保用户能进入心流状态使用工具。
> 设计目标：**让用户忘记自己在用什么工具**——像写 Word 一样自然，但有 AI 在后台。

### 8 B.1 心流的 4 个敌人 + 4 个解药

| 心流敌人 | 具体表现 | 我们的解药 |
|---------|---------|----------|
| ① 加载等待 | > 200ms 看不到反馈 → 焦虑 | 永远 < 100ms 给出反馈（占位符 / skeleton）|
| ② UI 切换 | 弹窗 / 新页面打断 | 全部 inline（diff / AI 建议都在原位置）|
| ③ 颜色刺眼 | 高对比度 / 多色块 | 单一主题色（赭黄 `#d4a574`） + 大量留白 |
| ④ 强迫决策 | 弹窗强制 同意/取消 | 永远有"稍后" / "Esc 跳过" |

### 8 B.2 视觉设计规范（huashu-design 风格）

#### 色板
- 主色：赭黄 `#d4a574`（**唯一一个高饱和色**，其他地方都低饱和）
- 背景：象牙白 `#fafaf7`（暖白，比纯白柔和）
- 文字：深咖 `#1a1a1a`
- 次文字：中咖 `#5a4a36`
- 弱文字：浅米 `#8b7e66`
- 高亮：墨绿 `#4a7a3a`（成功/接受）
- 警告：暗红 `#a83232`（拒绝/错误）

#### 字体
- 标题：**Songti SC / STSong**（衬线，有"书"的质感）
- 正文：**PingFang SC / Microsoft YaHei**（无衬线，长时间阅读不累）
- 代码 / 数字：**SF Mono / Menlo**（等宽，AI 输出时区分内容）

#### 排版
- 段距：1.6-1.8（**不**用 Word 默认 1.0）
- 字距：标题 -0.02em
- 留白：每段前后 0.5em
- 强调：**只有下划线**——不用粗体 + 斜体 + 大写（避免"乱"）

### 8 B.3 交互细节（4 大类）

#### 1) 键鼠
- ⌘K：悬浮编辑（**默认"建议"，不强制接受**）
- ⌘L：右侧抽屉（**不抢焦点**）
- ⌘R：底部抽屉（脚注插入位置）
- ⌘I：内联图片
- Tab：接受当前 AI 建议
- Esc：拒绝当前 AI 建议
- ⌘. （句号）：暂停所有 AI 操作
- 鼠标悬停 AI 输出 → 显示"结论 / 来源 / 边界"（F3）

#### 2) AI 输出展示
- **永远 diff 形式**，不"替换"
- 接受用高亮（绿 `#4a7a3a`），拒绝用删除线（红 `#a83232`）
- AI 信心分 3 档：高（实色）/ 中（半透明）/ 低（虚线 + ⚠ 提示）
- 滚动条永远不出现"自动滚动到 AI 输出"——尊重用户视线

#### 3) 错误处理
- ❌ 弹窗（破坏心流）
- ❌ 红屏（让用户崩溃）
- ✅ 内联红字 + 自动消失（3 秒后变浅）
- ✅ 一键撤销栈无限（F2）
- ✅ 出错时**保留草稿**——不能丢用户的字

#### 4) 加载与反馈
- 写 → 0ms 反馈（永远是即时的）
- ⌘K → 100ms 内显示 skeleton + "AI 思考中"
- ⌘L → 500ms 显示流式输出（**打字机效果**，不要等全部完成）
- ⌘R → 2-3s 显示研究列表（loading + partial results）
- 任何 > 3s 的等待 → 显示 "AI 慢？[Cancel] [Use Short Result]"

### 8 B.4 5 个"反心流"动作的红线（V0 必查）

- ❌ **绝不弹窗**（除非用户主动触发）—— ⌘K Diff 高亮是例外（**inline 在编辑器内**），不是浮动面板（详见 §六 B）
- ❌ **绝不强制 AI 修改**（默认"建议"，不"替换"）
- ❌ **绝不自动滚动**（AI 输出不影响用户视线）
- ❌ **绝不打断打字**（AI 处理在后台，不抢焦点）
- ❌ **绝不丢字**（任何操作失败必须保留草稿）

### 8 B.5 心流度量（V0 内测必收）

| 指标 | 目标 | 测量方式 |
|------|------|---------|
| 平均键鼠响应延迟 | < 100ms | 浏览器 DevTools Performance |
| AI 输出展示延迟 | < 500ms 首字 | 服务端打点 |
| 内测用户每日连续写作时长 | ≥ 60 分钟 | 自动埋点 |
| "Esc 拒绝率"（⌘K Esc 率） | < 30% | 行为埋点 |
| "⌘. 暂停"率 | < 5% | 行为埋点 |
| 草稿丢失事件 | 0 | 异常日志 |

### 8 B.6 4 类用户的心流差异（V0 内测时分别观察）

| 用户 | 心流特征 | 关键 UI 调整 |
|------|---------|------------|
| **方法论书籍作者** | 长时间单章写作（>1 小时）| 防眼疲劳 = 深色模式 / 字体可缩放 |
| **学术综述作者** | 多文档对照（>5 个 PDF）| 分屏视图（左原文 / 右脚注）|
| **长篇小说作者** | 频繁切换场景 / 伏笔 | 大纲树常驻 + ⌘L 全文搜索 |
| **自媒体 / 博客** | 短而快（< 30 分钟）| 模板开场 + 一键发布（V1） |

### 8 B.7 视觉规范 4 件套（huashu-design 已实现）

| 件套 | 用途 | V0 必做 |
|------|------|--------|
| **Hero Animation** | 应用启动 | ✅ |
| **Card-based Layout** | 主要内容容器 | ✅ |
| **Quote Block** | 引用 / 重点段落 | ✅ |
| **Diff Highlight** | AI 修改展示（绿/红，**页面内 inline**）| ✅ ← 2026-07-15 决策：inline 优于 floating panel |

### 8 B.8 暗黑模式（V0 Week 2 实测）

- ❌ **不**做"刺眼白底"（强光下刺眼）
- ✅ 自动跟随系统（macOS / Windows 暗色模式）
- ✅ 暗色模式色板：背景 `#1a1a1a` / 主文字 `#e8e6e0` / 主色不变（赭黄）
- ✅ 内测时让用户切换 2 种模式，**选择使用更多的一种作为默认**

### 8 B.9 V0 心流测试 3 大方法

1. **观察法**：招募 3 名内测用户（每个 1 小时），不告知任何产品功能，让他自己"想写啥就写啥"，观察他在哪里停顿 / 退出 / 切走 / 抱怨
2. **问卷法**：内测结束后发 3 个问题：
   - "你的心流在哪里被打断？"（开放式）
   - "哪个功能让你更专注？"（多选）
   - "如果只能留 1 个功能，你选哪个？"（单选）
3. **数据法**：自动埋点收集 Esc 拒绝率 / ⌘. 暂停率 / 连续写作时长

### 8 B.10 V0 Week 1 心流验证 checklist

- [ ] 本机启动应用 ≤ 1 秒（不闪屏 / 不弹窗）
- [ ] 输入文字 → 0ms 反馈（无延迟感）
- [ ] ⌘K 触发 → 100ms 内 skeleton + 500ms 内流式输出
- [ ] AI 输出**默认是 diff**，不替换（Esc 一键拒绝）
- [ ] 任何错误**保留草稿**（关闭浏览器重启应用不丢字）
- [ ] 暗色模式自动跟随系统
- [ ] **3 名内测用户中至少 1 人连续写 ≥ 30 分钟**（V0 退出条件之一）

## 九、价值主张 5 条

> 为什么专业作者应该关注 WritCraft，而不是继续在 Notion + ChatGPT 里凑合

| # | 价值主张 | 背后逻辑 |
|---|---------|---------|
| **① AI 内联占比 ≥30%** | M2.7-highspeed <200ms，让 AI 改写真正实时发生，而不是等 3 秒弹出一个对话框打断思路 | 速度是心流的敌人；200ms 是人类感知"即时"的边界 |
| **② Plan Mode 防散** | 写长文最怕写着写着不知道自己在写什么——Plan Mode 在左侧显示结构锚点，随时可以把用户拉回来 | 不是强制大纲，是可视化坐标 |
| **③ 引用脚注自动化** | 学术 / 咨询场景引用格式繁杂——APA7 / MLA9 / Chicago17 自动生成，不用手动查格式 | 引用格式错误是专业度的最大杀手 |
| **④ 多模态内联** | 图像生成 + 文本写作在同一界面完成，不用切 Midjourney / 即梦再手动插图 | 工具切换是写作最大的外部干扰 |
| **⑤ 跨章引用复用** | 《原则》写了 500 页，某一章引用了另一章的观点——⌘L 全局查询 + @chapter 引用，全项目生效 | 长文写作的核心挑战是结构一致性，不是单句质量 |

## 十二、风险与退出条件

### V0 退出条件（Continue / Pivot / Abandon）

**Continue（满足全部 3 条）**：

- ✅ 10 名内测作者中 ≥7 人每天使用 ≥30 分钟（DAU 活跃）
- ✅ ⌘K 修改接受率 ≥60%（说明 AI 建议被用户信任）
- ✅ Plan Mode 完成率 ≥50%（说明大纲→写作路径被用户接受）

**Pivot（满足任一）**：

- ⚠️ TipTap + MiniMax 集成遇技术瓶颈 → 换用 Lexical 重写或 OpenAI API 直连
- ⚠️ M2.7 延迟 >500ms → ⌘K 降级为"异步确认模式"（1–3 秒可接受）
- ⚠️ Plan Mode 接受率 <30%（无大纲派强烈抵触）→ Plan Mode 降级为可选入口，V0 主路径改为"直接写作 + ⌘K"

**Abandon（满足任一）**：

- ❌ 2 周后仍无 5 名内测写作者（用户招募失败）
- ❌ 内测作者平均使用时长 <10 分钟 / 天
- ❌ MiniMax API 异常 >1 天不可用（无备选方案）
- ❌ TipTap 技术难点 >3 天未解决（无内部能力解决）

### 立即暂停触发器

| 风险 | 触发条件 | 暂停原因 |
|------|---------|---------|
| MiniMax API 异常 | >1 天不可用 | V0 核心依赖断裂 |
| TipTap 技术难点 | >3 天未解决 | V0 技术路径不通 |
| 内测作者负面反馈 | >3 条明确负面（"不如 Notion" / "无法使用"）| 产品方向存疑 |
| Max 可用时间断崖 | 单周可用时间 <5h | V0 无法按计划交付 |
