### T8 方法论漏洞

1. **D1 犯了诉诸历史谬误（Appeal to History）**：用"某事物存在时间长但未普及"来证明"新形式也必然失败"——这是经典逻辑错误。Scrivener Corkboard 失败不等于 Plan Mode 在 AI 加持下不 work。
2. **D9 自身的建议未经验证**：T8 说"聚焦单一用户类型"，但没有提供证据证明这个策略在写作工具市场有效（参考 Notion 早期聚焦极客/创业公司 vs 最后做成通用工具）。
3. **T8 金句 3 自我矛盾**：金句 3 说"AI 修改应该适应写作者的节奏，不是让写作者适应 AI 的节奏"——这反对的是实时逐句 Diff，但 T7 的 P0-H2 正是逐句 Diff。T8 的金句实际上**否定了 T7 的 P0 核心功能**，但 T8 没有意识到这个矛盾。
4. **T8 的"严重程度"分配不一致**：D2（TipTap 集成）被标 P0，D10（隐私合规）也被标 P2 但实际是 V2 问题；D1（Plan Mode）被标 P1 但实际可能更严重，因为影响核心假设。

### 质疑 N1（原 T8 无）：T7 V0 可行性 3/5 分与"无 PRD"的事实存在根本矛盾

- **被质疑对象**：T7 综合评分体系 / T0 时间线
- **质疑类型**：内部一致性漏洞
- **原结论**：T7 给予 V0 可行性维度 **3/5，置信度 M**，结论是"可以继续"；T0 时间线要求 Day 7 启动 V0 开发
- **质疑理由**：
  - V0 开发前置条件：必须有完整的 PRD（功能范围 + UX 规格 + API 设计 + 技术选型文档）——这是任何软件工程的常识
  - T7 的"PRD 五问"（Q1-Q5）**不是 PRD**：它们是产品决策问题的清单，不是可以交给工程师开发的功能规格文档
  - 没有任何一个 T1-T8 的输出物包含：UI 布局说明、交互流程图、API endpoint 设计、数据模型完整定义、验收标准
  - **T7 的 5 维评分体系暗含了一个隐含假设**：已经有足够的细节可以做 0-1 开发决策——但实际上什么都没有
- **极限反例**：Day 7 开始 V0 开发，工程师问"⌘K 触发后悬浮层的层级关系是什么？""接受拒绝的状态机是什么？""章节节点树的数据结构是什么？"——开发团队无法回答，因为没有任何文档定义过
- **建议**：T9 路线图之前，**必须强制输出一份正式 PRD**，至少包含：(1) 核心用户流程 + UI 草图；(2) TipTap 扩展点的技术设计；(3) MiniMax API 的调用方式设计；(4) V0 功能范围的精确边界定义
- **置信度影响**：T7 综合判断"可以继续"→"条件性继续（正式 PRD 交付后）"

### 质疑 N2（原 T8 无）：King + Murakami 明确反对 AI 写作——T7 Plan Mode 前提与 T3 证据直接矛盾

- **被质疑对象**：T7 Plan Mode P0 定级 / T3 作家访谈结论
- **质疑类型**：因果矛盾 + 样本偏差
- **原结论**：T7 将 Plan Mode 列为 **P0-H3**（5星优先级），理由是"4/4 文体均强调先计划后写作"；T2 的 SOP 矩阵也支持这个结论
- **质疑理由**：
  - **T3 的直接证据**：Murakami 2026 明确表态反对 AI 参与写作过程；King 2024 对 AI 持警惕态度；T3 的作家访谈综合表显示这两人是"AI 明确反对派"
  - **T7 的内部矛盾**：T7 的"自我质疑"中承认了"无大纲派（King、Murakami）可能不用 Plan Mode"，但将这个担忧降级为"答：Plan Mode 是可选入口"——**这个回答没有解决矛盾，只是回避了它**
  - **关键问题**：King + Murakami 代表着写作工具市场中最有影响力的用户群体（他们的写作方法论被大量学习模仿），如果 WritCraft 的核心使用路径（先 Plan Mode 再写作）天然排斥他们，T7 的"4/4 文体"论证实际上是**用支持大纲派的作家验证了大纲的价值**，而非证明了"无大纲派也会接受 Plan Mode"
  - **T8-D1 抓住了这个问题的正确方向但用了错误的论证**：T8 说"Scrivener Corkboard 失败说明习惯无法改变"——但真正的问题不是"习惯"，而是**最高价值的早期采用者（愿意容忍不完善的极早期用户）可能恰恰是无大纲派**，因为他们的写作哲学是"发现性写作"，不需要也不想要 AI 规划框架
- **极限反例**：V0 早期用户主要是方法论书籍写作者（大纲派），第二波扩张到学术综述时发现"写书的"根本不接受 Plan Mode，导致产品需要重构核心交互路径
- **建议**：V0 Plan Mode 应明确定位为"**可选辅助**"而非"核心入口"；V0 的最小可行路径应允许用户**跳过 Plan Mode 直接写作**；在用户访谈中专门测试无大纲派作家的接受度（而不是只验证大纲派）
- **置信度影响**：T7 Plan Mode P0 优先级 → **P1（降级）**；T7 产品-市场匹配度 4/5 MH → 3/5 M

### 质疑 N3（原 T8 无）：T7 的 V0 成本估算可能少算一个数量级

- **被质疑对象**：T5 MiniMax 成本模型 / T7 商业潜力
- **质疑类型**：假设未验证 + 数量级估算错误
- **原结论**：T5 估算"100 用户 × $170-190/月"；T7 基于此认为成本优势是主流方案的 1/4-1/5
- **质疑理由**：
  - T5 的成本模型基于"日常对话场景"（每次 API 调用消耗约 500-2000 tokens）
  - **写作 IDE 的实际消耗模式完全不同**：用户每小时可能触发 20-50 次 ⌘K 修改（每次修改涉及选中文本 + AI 建议 + 用户决策 + 接受/拒绝），每次 ⌘K 调用的 token 消耗远超普通对话
  - 更关键的是：**写作是长时间沉浸活动**。专业写作 sessions 通常 1-3 小时，假设 100 用户 × 每天 1 小时 × 50次 ⌘K/小时 × 500 tokens/次 × 30天 = **75 亿 tokens/月**——远超 T5 估算的量级
  - 即使数字是 10 倍保守估计，1 亿 tokens/月 × $0.30-0.60/M = **$300-600/月**——已经接近 T5 估算的上限
  - T8-D6 指出 M3 涨价风险，但没有指出**写作场景的实际消耗量级可能远超 T5 假设**
- **极限反例**：V0 上线后，5 名活跃用户（每天 2 小时写作）的月消耗就达到 5000 万 tokens，成本 $1500-3000/月——100 用户时成本根本无法控制
- **建议**：T9 前必须做**真实消耗量级测试**（用典型写作 session 模拟，测量实际 token 消耗）；成本模型必须基于写作场景的实测数据，而非对话场景的类比估算
- **置信度影响**：T7 商业潜力 3/5 M → 2/5 L（成本优势存在根本性不确定性）

### 质疑 N4（原 T8 无）：中文排版被 T7 标为 P1-M，但"流失 Notion"逻辑要求它应该是 P0-L

- **被质疑对象**：T7 P1 风险评级 / T6 design-patterns
- **质疑类型**：严重程度 × 置信度不匹配
- **原结论**：T7 将"中文排版质量"列为 **P1，置信度 M**；理由是"Typography 基础中文标点；CSS hack"
- **质疑理由**：
  - T7 Q3 中说"排版差则用户立即流失 Notion"——这意味着中文排版是**留存的关键因素**，不是"做得不好也能忍"的加分项
  - **P1 的定义**（T7 自身标准）："V1 必须做，V0 尽量做"。如果排版差导致立即流失 Notion，那 V0 排版差就等于 V0 失败——这应该是 **P0 条件**而非 P1 弹性项
  - 更严重的是：T7 给中文排版的置信度是 **M（中）**——但"CSS hack"方案根本不是生产级解决方案，它是概念验证阶段的临时手段
  - T6 的 design-patterns 分析提到 TipTap 的中文支持需要额外的 CSS + Font 配置，但这**没有在 T7 的技术路径中体现为明确的工程工作量估算**
- **极限反例**：V0 开发到第 3 周，中文排版始终无法解决"首行缩进 2 字符 + 中文标点 + 禁排规则"的组合问题，团队发现需要深度改 TipTap 渲染引擎，工时从 3 天变成 3 周，导致 V0 交付延期
- **建议**：中文排版应升级为 **P0 验证条件**；在技术验证 Sprint（D2 建议）中必须包含"中文排版可行性"的具体测试（用真实中文文本跑通 TipTap 渲染）
- **置信度影响**：T7 技术可行性 3/5 M → 2/5 L（中文排版是 P0 风险但被低估为 P1）

### 质疑 N5（原 T8 无）：T7 的"V0 跑通"指标——7 天留存 ≥ 40% 和"5 人说比 Notion 好用"都无意义

- **被质疑对象**：T7 V0 成功指标 / T7 Q5
- **质疑类型**：指标定义空洞 + 因果混淆
- **原结论**：T7 定义 V0 成功标准：M3 里程碑是"7 天留存率 ≥ 40%；≥1 用户完成完整流程并反馈'比 Notion 好用'"
- **质疑理由**：
  - **7 天留存 ≥ 40% 的问题**：写作是**周频行为**（不是日频），专业作者可能每周写作 1-2 次。V0 的早期用户（愿意容忍产品不完善的极早期用户）可能每 2-3 天才打开一次。那么"7 天"的时间窗口设计是任意的——如果把窗口延长到 14 天，留存率可能会显著上升（或下降），但 T7 没有说明为什么选 7 天
  - 更根本的：**留存的前提是用户有东西可写**。V0 第一天就跑通的用户，可能因为"没有写作素材/灵感"而 7 天后不回来——这不是产品问题，是用户预期管理问题
  - **"5 人说比 Notion 好用"的问题**：这是一个**主观感受指标**，没有任何量化标准。"比 Notion 好用"是指同样任务更快？更愉快？输出质量更高？——如果没有具体任务定义和对比基准，这个反馈在 V0 迭代中毫无指导价值
  - T7 的"失败条件"是"5 人中 4 人说不如 Notion"——这意味着只要 1 人说好就算成功，这个阈值低到没有意义
- **极限反例**：V0 M3 测试，7 天后 5 名用户中 2 人留存（留存率 40%），但这 2 人都是"尝鲜者"而非目标用户，真正的方法论书籍写作者全部流失——V0 通过了数字指标但产品方向已经走偏
- **建议**：V0 成功指标应包含**定性维度**：(1) 用户是否在 14/30 天后仍主动打开（而非因为提醒）；(2) 用户是否向同类型其他人推荐（净推荐值 NPS）；(3) 用户是否愿意为 V0 功能付费（而非只用免费部分）
- **置信度影响**：T7 V0 可行性 3/5 M → 2/5 L（成功指标无法区分真正的产品-市场匹配和偶然的早期采用）

## 五、结论：T1-T7 哪些结论站得住

### 站得住的（高置信度）

1. **市场空白是真实的**：无产品同时具备结构化大纲 + Cursor 式 AI 内联 + Plan Mode + 多模态。T4 竞品横评证据充分。
2. **TipTap + MiniMax 技术上可行但未实测**：D2 正确，这是 V0 最大的技术风险。
3. **6 大 Cursor 范式中 5 个可移植**：T1 的分析逻辑清晰，Accept/Reject、⌘K、⌘L 的写作化改造有充分依据。
4. **差异化壁垒清晰**：逐句 Diff、结论溯源、研究内联——6 款竞品确实全部缺失这 5 个功能。
5. **MiniMax 成本优势在模型层是真实的**：M3 1M 上下文 + image-01 $0.0035/张 + 中文优化，是真实的差异化优势。

### 需要补充证据或降级置信度的

1. **Plan Mode 价值被高估**：N2 显示 King/Murakami 等顶级用户反对 AI 介入写作过程；Plan Mode 应降级为 P1 而非 P0。
2. **V0 可行性 3/5 过于乐观**：3 个 P0 风险（集成、中文排版、无正式 PRD）均未解决就给 3/5 是自欺欺人；实际应为 2/5。
3. **成本优势存在数量级不确定性**：N3 显示 T5 的成本模型基于错误场景假设，实际消耗可能高 10 倍。
4. **用户画像需要重新定义**：T7 的"5 类用户"泛化导致 V0 功能范围无法收敛；N2 进一步证明无大纲派可能是被错误排除的目标用户。
5. **V0 时间线可行性无依据**：没有 PRD、没有实测集成、没有中文排版方案，却要求 Day 7 启动开发——这是信念而非规划。

### 需要立即行动（才能继续的 P0 条件）

1. **实测 MiniMax + TipTap 集成**（2-3 天技术 Sprint）
2. **输出正式 PRD**（不是 5 问清单，是可执行规格文档）
3. **实测中文排版方案**（用真实中文文本在 TipTap 上跑通基础排版）
4. **重新做写作场景 token 消耗量级估算**（基于真实写作 session）
